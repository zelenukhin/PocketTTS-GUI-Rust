# BENCHMARKS — методика и результаты

## Методика

- Инструмент: `target/release/bench.exe` (исходник `crates/app-core/src/bin/bench.rs`).
- Фраза: «Стр+елки час+ов показ+ывали п+олночь, а стрелк+и заст+ыли на пост+ах.» (~70 символов, ~5 с аудио), seed 42, temperature 0.3, decode_steps 1.
- Прогрев: 5 чанков (в замер не входят). Измерение: 100 чанков; аудио отбрасывается сразу (инструмент не копит память — иначе ложная утечка).
- Память: Working Set / Private Usage (GetProcessMemoryInfo), дельта от старта; VRAM: nvidia-smi total Δ (WDDM per-process недоступен) + запись bench-строки.
- RTF = время генерации / длительность аудио (меньше — лучше; RTF 0.5 = вдвое быстрее реального времени).
- Каждый чанк = полный цикл: prepare → BPE → text_conditioner → voice (кэш) → main ×N кадров → flow ×steps → decoder. Ошибка CUDA-прогона не глушится: bench падает с кодом ≠ 0.

Фикс: session_builder всегда передаёт `use_tf32=0` (в прогоне 1 дефолт
провайдера TF32=ON действовал на conv-графах — доказано `ep_probe`, см.
CUDA_FEASIBILITY). Профилирование выключено.

| tag | модель | device | mean s/chunk | p95 | RTF | WS Δ MB | Priv Δ MB |
|---|---|---|---|---|---|---|---|
| cpu-fp32-slow | ru-v2-slow | cpu | 3.384 | 4.085 | 0.657 (1.5x) | +506 | +499 |
| cuda-fp32-slow-tf32off | ru-v2-slow | cuda | 2.512 | 2.999 | **0.487 (2.1x)** | +919 | +3556 |
| cpu-fp32-fast | ru-v2-fast | cpu | 2.506 | 2.730 | 0.500 (2.0x) | +483 | +476 |
| cuda-fp32-fast-tf32off | ru-v2-fast | cuda | 1.350 | 1.461 | **0.269 (3.7x)** | +896 | +3538 |

**Сравнение с прогоном 1 (влияние отключения TF32):**

| Конфиг | RTF run1 (TF32 default) | RTF run2 (tf32=0) | Δ |
|---|---|---|---|
| cpu-fp32-slow | 0.628 | 0.657 | +4.6% |
| cuda-fp32-slow | 0.506 | 0.487 | −3.8% |
| cpu-fp32-fast | 0.528 | 0.500 | −5.3% |
| cuda-fp32-fast | 0.306 | 0.269 | −12% |

Вывод по TF32: различия **в пределах шума стенда (±10%, параллельная нагрузка
менялась между прогонами)** и без систематического замедления от tf32=0 —
локальный вывод: TF32 не давал этим графам ускорения (Gemm-пути он и так не
менял по числам пробы; conv-пути — малая доля времени). Гарантия строгого
FP32 получена без измеримой цены. Время жизни CPU-fallback/WDDM — прежние
оговорки.

Общий вывод не изменился: лучшая конфигурация — **CUDA FP32 + ru-v2-fast**
(run2: 3.7x реального времени; run1: 3.3x — берём консервативно 3.3–3.7x).

(Полная таблица прогона 1 — в `out/bench_run1.log`; RTF-строки — в сравнении
выше. Вывод по памяти прогона 1 остаётся в силе: WS-дельта за 100 чанков ≈
размер модели+сессий, роста чанк-к-чанку нет; CUDA держит ~3.5 ГБ private
bytes хост-памяти на рантайм-контекст; длительности аудио CPU↔CUDA на
одинаковых seed совпадают (515.4/515.5 с) — EOS на GPU идентичен.)

### Детерминизм

CPU FP32, seed 42, chunk_index 0, два отдельных процесса: **WAV побитово идентичны** (`cmp` = 0). CUDA-детерминизм между запусками не проверялся (поток на GPU не обязан быть побитово стабильным; при seed-политике GUI это допустимо — сравнение CPU↔CUDA сэмпл-в-сэмпл не требуется).

## A4: воркеры — детерминизм и производительность (2026-11-08)

Методика: `synthesize --workers N`, модель ru-v2-slow, FP32, seed 42; короткий
текст (3 чанка) и фрагмент книги (47 чанков, 262 с аудио); RAM — пик WorkingSet
сэмплированием во время работы; VRAM — nvidia-smi во время работы.

### Детерминизм

| Сравнение | Результат |
|---|---|
| CPU 1w vs 2w (3 чанка) | **побитово идентичны** (WAV cmp = 0) |
| CPU 1w vs 2w (47 чанков) | **побитово идентичны** |
| CUDA 1w vs 2w (3 и 47 чанков) | **побитово идентичны** (внутри одного EP; seed+индекс не зависит от воркера) |
| CPU vs CUDA | длительности совпадают (18.45/262.39 с), PCM отличается (max ~2278/32768 ≈ 7% — разные EP, ожидаемо) |
| seed = −1 | base_seed фиксируется один раз на задание и печатается (пример: 1794171538980752000) — прогон повторяем указанием этого seed |

### Производительность (47 чанков, ru-v2-slow)

| Конфиг | RTF | Wall, с | Пик WS, МБ | VRAM в работе |
|---|---|---|---|---|
| CPU 1w (3 потока ORT) | 0.728 | 191.0 | 934 | — |
| CPU 2w (по 3 потока) | **0.558** (−23%) | 146.4 | 2367 (2 движка) | — |
| CUDA 1w | 0.531 | 139.6 | 1028 | ~2.0 ГБ |
| CUDA 2w | **0.465** (−12%) | 122.3 | 1237 | ~3.8 ГБ (2 движка) |

Выводы:
- **CPU 2w — уверенный выигрыш** (×1.30 к скорости за +1.4 ГБ RAM) —
  рекомендован для CPU-режима.
- **CUDA 2w — скромный выигрыш** (×1.14) за +1.8 ГБ VRAM: каждый кадр гоняет
  стейты через PCIe, второй контендится за тот же GPU; **не включать
  многоворкерный CUDA по умолчанию** без io-binding (см. CUDA_FEASIBILITY).
- Память нескольких сессий: CPU 2w ≈ 2×0.9 ГБ WS; освобождение подтверждено:
  после задания WS падает (sampler фиксирует пик только в работе), VRAM
  возвращается к базовой сразу после exit (611 МБ).
- Backpressure: буфер переупорядочивания ≤ окна (замеры 1–4 при cap 4).

## Стресс 1000 чанков (различные фразы книги, 2026-11-08)

Методика: `bench --text-file <книга>` — 107 различных фраз (реальный
подготовленный текст с ударениями, циклически), прогрев 10 чанков отдельно,
память (WS/Private/GPU-total) каждые 10 чанков в CSV, аудио инструментом не
хранится, после прогона движок дропается и память меряется снова. Тренд —
наклон МНК по steady-точкам.

| Конфиг | RTF | mean/p95, с | WS: после прогрева → конец | Private: → конец | GPU: → конец | Тренд private, МБ/1000 чанков | После drop: private/GPU |
|---|---|---|---|---|---|---|---|
| cuda-fp32-slow | 0.520 (1.9x) | 1.99 / 4.43 | 926 → 831 МБ | 3581 → 3584 | 2753 → 2785 МБ | **+1.1** | 1106 / 737 МБ (−2478 / −2048) |
| cuda-fp32-fast | 0.312 (3.2x) | 1.19 / 2.63 | 893 → 800 МБ | 3530 → 3534 | 2773 → 2766 МБ | **+0.9** | 1103 / 730 МБ (−2430 / −2036) |
| cpu-fp32-slow | 0.650 (1.5x) | 2.49 / 6.08 | 511 → 514 МБ | 500 → 505 | 607 → 592 МБ | **+1.4** | 18 / 592 МБ (−487 / +0: полный возврат) |

Выводы (все три прогона):
- **Утечки памяти нет ни в одном режиме**: private bytes растёт на 0.9–1.4 МБ
  за 1000 чанков (≈1 КБ/чанк — в пределах шума аллокаций); WS стабилен/снижается;
  VRAM-тренд ±15 МБ/1000 — шум арены. Проблема Python pocket-tts («~9 МБ commit
  на чанк», лечившаяся перезапуском воркеров) в Rust-движке не воспроизводится.
- **Ресурсы освобождаются**: после `drop(engine)` — CPU-режим возвращает всё
  (private 505→18 МБ); CUDA-режим возвращает модель и арену (private −2.4…−2.5 ГБ,
  VRAM −2.0 ГБ), остаётся контекст CUDA (~0.7 ГБ GPU / ~1.1 ГБ private — умирает
  с процессом).
- RTF на разнородном корпусе выше эталонной фразы (короткие фразы дороже
  относительно), порядок конфигураций сохраняется: fast-CUDA 3.2x > slow-CUDA
  1.9x ≈ slow-CPU 1.5x.

CSV: `out/stress_*.csv` (фазы start/steady/end/after_drop), графики:
`out/memory_{private,ws,gpu}.svg` (генератор `tools/plot_memory.py`).
