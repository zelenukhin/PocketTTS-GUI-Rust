## 1. Реальная архитектура текущего CPU-синтеза

Проверено по коду (`pool.rs`, `pipeline.rs`, `persistent.rs`, `worker.rs`,
`job.rs`, `batch.rs`, `pocket.rs`) и подтверждено измерениями.

**Три механизма:**

- **A. Параллельные чанки одного файла** — реализован и активен. Каждый
  воркер = собственный поток + собственный `Pocket` = **5 ONNX-сессий**
  (main/flow/decoder/encoder/text-conditioner). Чанки раздаются через
  ограниченные очереди со скользящим окном (backpressure), сборка строго по
  порядку. `workers` (GUI, авто для CPU = **2**) управляет именно этим.
- **B. Параллельные файлы пакета** — на CPU **НЕ реализован**: постоянный
  пул `persistent.rs` включается только для CUDA-пакетов с ≥2 кандидатами
  (`job.rs:737` — `pool_enabled = device == Cuda`). CPU-пакет идёт
  последовательным путём `execute_batch_sequential`: **модель загружается
  заново на каждый файл** (12 Pocket на пакет из 12 файлов). Настройка
  «Воркеров» внутри каждого файла действует (механизм A), но файлы между
  собой не параллелятся.
- **C. Настоящий ONNX tensor batching** — не реализован. Технически
  основной граф `flow_lm_main` — stateful (KV-cache, покадровый цикл
  декодирования с EOS-логикой и анти-повторами в Rust); объединение разных
  чанков в один batched-запрос потребовало бы батчированных состояний и
  синхронного EOS для всего батча. Заключение: применимость сомнительна,
  выигрыш неочевиден, реализацию не считать приоритетом (и она не входит в
  это исследование).

**Потоки ORT:** `LoadOptions.threads` (GUI «потоков», дефолт 4, clamp 1..16)
→ `with_intra_threads` каждой из 5 сессий; `allow_spinning=0`. Inter-op не
задаётся (ORT default = 1 пул на сессию). Один Pocket с T=4 создаёт
десятки потоков (наблюдались 20–36 на процесс) — большая часть спит.

**Загрузка модели на CPU дешёвая**: 0.8–2.1 с на Pocket (events.jsonl:
FP32 W1 1114 мс, W2 1339–1365 мс параллельно, W4 2048–2066 мс; INT8
814–1339 мс). Это принципиально отличается от CUDA и обесценивает
«переиспользование модели» как главный аргумент CPU-пула.

## 6. Побитовый паритет WAV (SHA256)

- **WAV зависит только от T и не зависит от W и от пути**: seq(T4) ≡
  pool W1(T4) побитово по всем 12 файлам (FP32 и INT8); одиночный файл:
  W1T2 ≡ W2T2, W1T1 ≡ W2T1 ≡ W4T1, W1T4 ≡ W2T4. Повторы (n=2–3) — тот же
  хеш. Причина различий между T — порядок редукции в intra-op потоках ORT
  (численно эквивалентные, но не побитово идентичные результаты).
- Следствие: переключение W безопасно для детерминизма; смена T меняет
  байты (как и смена устройства/точности). FP32 vs INT8 не сравнивались.

## 8. Рекомендации (НЕ внедрены — только предложения)

**Одиночный файл (механизм A):**
- Сбалансированно: **W=2, T=4** (текущий дефолт GUI «авто=2, потоков 4»)
  — −22…−25% к W1 при ~1.6 ГБ (Slow FP32). Менять не нужно.
- Максимум: W=4, T=1 — ещё −6…−9% (у Fast INT8 до −8%), но +1.3 ГБ и
  рост латентности первого чанка; рекомендовать только как осознанный
  выбор при свободной RAM.

**Пакет файлов (механизм B — сегодня на CPU отсутствует):**
- Постоянный CPU-пул **выгоден**: W2T2 даёт −33% (FP32) / −37% (INT8)
  к текущему последовательному пути; W4T1 — −38% / −46%, но 3.1 ГБ (FP32)
  и латентность первого файла ×2.4.
- **Сбалансированная рекомендация: pool W=2, T=2** (−33%, ~1.3 ГБ);
  максимальная производительность: W=4, T=1 (только при достатке RAM).
- Отдельные настройки для FP32/INT8 не требуются: соотношения W/T
  одинаковы, INT8 просто равномерно быстрее на 25–35% и вдвое легче.
- Выигрыш пула на CPU складывается в основном из параллелизма, а не
  устранения загрузок (загрузка <2 с); переиспользование модели —
  приятный, но вторичный эффект (−11%).

**Для GUI (предложения, не внедрять в этом этапе):**
- `auto` для CPU-пакетов = **2 параллельных файла × T=2..4** (учитывать
  число логических CPU: min(2, logical/4) на слабых машинах).
- Разделить настройки «параллельные файлы» и «воркеры чанков» при
  внедрении CPU-пула (сегодня «Воркеров» на CPU управляет только чанками).
- Профили «Экономичный» (W1T4) / «Максимальная скорость» (W4T1)
  оправданы; автоограничение W по доступной RAM (порог ~1 ГБ/воркер
  FP32, ~0.6 ГБ INT8) — полезно.
- Tensor batching (C) не рекомендовать к реализации (stateful-графы).

## 9. Ограничения

- n=1 для большинства конфигураций; повторы (n=2–3) только финалистов —
  разброс повторов ≤±1.5%, выводам не противоречит.
- CPU-утилизация в % не профилировалась (наблюдалось число потоков
  процесса); тест S (короткий файл) отдельно не гонялся — накладные
  расходы оценены по load_ms и латентности первого файла.
- Fast-модель в пакетном тесте не гонялась (поведение следует тем же
  соотношениям одиночного файла); batch для Hybrid/многопроцессность на
  CPU не исследовались (по P2B.2–P2B.3 процесс ≠ преимущество).
- Стенд 4C/8T: на CPU с большим числом ядер оптимум может сместиться к
  большему W (проверять по той же методике).

### Побитовый паритет (контроль)

Sequential W2T4 ≡ Pool W2T4 **побитово по SHA256** на всех 4 моделях
(Slow/Fast × FP32/INT8, 12/12 файлов; Slow FP32 — в двух независимых
парах прогонов) и на коротком корпусе (4/4). Правило «WAV зависит только
от T (и модели/точности/seed), а не от W и не от seq-vs-pool» подтверждено
и для чанк-параллельного W=2 в последовательном режиме, и для
файл-параллельного пула. Seed-политика сопоставима (pool использует base
seed 42 на каждый файл, как и CLI-эталон).

### Проверка корректности прогонов

12/12 (и 4/4) WAV в каждом прогоне; дублей/пропусков нет (claim-очередь);
зависших процессов нет (все exit в пределах timeout); peak RAM после
выхода процессов возвращается к базовому уровню.

### Итоговые рекомендации (уточнённые)

**А. Нужен ли постоянный CPU-пул?** Да: реальный выигрыш к нынешнему GUI
W2T4 — **1.26–1.44× по wall (−21…−30%)** в зависимости от модели; лучшие
результаты у Fast INT8 (1.44×) и Fast FP32 (1.34×), Slow — 1.26–1.30×.
Прежние «−33…−46%» относились к искусственному эталону W1T4 и как
заявление о выигрыше над GUI некорректны.

**Б. Сколько воркеров?** Сбалансированно — **W=2** (1.26–1.44×, ≤1.7 ГБ).
Максимум — W=4/T1 (Slow FP32 1.35×, −25.7%), но 3.3 ГБ RAM и латентность
первого файла 50.6 с против 17.4 с у GUI: только осознанный выбор.

**В. Какое T?** Оставить **T=4** (не хуже T=2, побитовая совместимость,
меньше изменений). W2T2 не является победителем.

**Г. Схема настроек для GUI (предложение).** Разделить: «Параллельные
файлы пакета» (W пула, auto=2) и «Воркеры чанков одиночного файла»
(существующая настройка, auto=2); T остаётся общей. Пресеты:
«Экономичный» W=1, «Обычный» W=2, «Максимум» W=4 (только pool-пакеты).

**Д. Адаптивное Auto.** `W_auto = clamp(1, floor(logical_cpus / 4), 4)`
(8 логических → 2; 16 → 4), дополнительно ограничить доступной RAM:
`W ≤ free_ram_gb / (FP32 ~1 ГБ | INT8 ~0.6 ГБ на воркер)`, минимум 1.
Не привязываться жёстко к 4C/8T стенда.

### Ограничения контрольной серии

- n=2 только для Slow FP32 (seq/pool W2T4/W4T1); остальные — n=1
  (разброс повторов основной серии ≤±1.5%; приоритеты бюджета соблюдены).
- Fast INT8/FP32 pool W2T2 и W4T1 в контрольной серии не мерились
  (основная серия: одиночный файл — масштабирование аналогично Slow).
- Slow INT8 короткий seq и Fast-короткий пакет не мерились (оценка по
  пропорции основной серии).
- CPU utilization в % достоверно не измерялся (нет счётчика в обёртке);
  косвенные индикаторы — число потоков процесса и латентности файлов.
- Общий бюджет контрольных измерений ≈ 33 мин (лимит 35), без повторов
  заведомо проигрывающих вариантов.
