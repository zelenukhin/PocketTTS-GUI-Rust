# Исследование многопроцессного CPU-пула (перед G6.6)

Дата: 2026-11-12. Исходный/итоговый HEAD `d515324` → коммит этого этапа
(см. HANDOFF). Production-код не менялся: использован существующий
диагностический `diag_p2b3` (поддерживает `--device cpu --precision`,
`--workers`, `--expect-processes`, общую claim-очередь и межпроцессный
readiness gate) — новых правок трекаемых инструментов не потребовалось,
NAS-бэкап не создавался (изменений кода нет; последний верифицированный
бэкап `350a39b` актуален для кодовой базы). Сырые данные — `out/cpu_multiprocess/`.

## 1. Архитектура теста

N процессов `diag_p2b3 hybrid --device cpu` с общей очередью
(`claim_XX.lock`, create_new — файл забирает ровно один воркер) и общим
каталогом WAV; готовность — флаги `ready_<pid>.flag` + гейт
(`ready_gate`-событие с полем `timeout`). Групповой launcher
`out/cpu_multiprocess/run_group.ps1`: внешний stopwatch на всю группу
(старт до первого процесса, стоп после выхода всех), сэмплер 250 мс,
суммирующий Private Bytes / потоки / CPU-time ВСЕХ живых процессов (пик =
max суммы; CPU-time — по per-PID накоплению последних живых значений),
watchdog-таймаут 900 с с `Stop-Process -Id` только своих PID.

Гейт корректен во всех прогонах: `ready_gate.seen == expect`,
`timeout=false`, ожидание ≤ 73 мс. Динамическая очередь (не статическое
распределение): claim-события показывают свободный воркер любого процесса
берёт следующий файл.

## 2. Стенд

i7-6700K 4C/8T, 16 ГБ, Win10 19045, «Высокая производительность», ORT
1.23.2 CPU, release-бинари HEAD `d515324`. Корпус main12 (12 TXT, 77
чанков, 367.1 с аудия). Параметры: seed 42, temp 0.3, steps 1, EOS
−4/5/3, anti-repeat on, brightness 8 дБ, denoise off, паузы 1.0/0.9,
max_tokens 50, WAV. Прогоны строго поочерёдные.

### Аномалия и её обработка

Первый прогон A1 дал 722 с (per-file gen в 3–14× хуже нормы при тех же
аргументах; готовность/очередь в норме) — внешний выброс среды (фоновая
нагрузка). По правилу одного повтора повторён: 151.0 с, соответствует
прошлой серии (158.1/157.9). Выброс исключён из статистики, зафиксирован
здесь.

## 4. Побитовый паритет WAV

- A: 1×2/T4 ≡ 2×1/T4 (12/12 SHA256, оба прогона) и ≡ эталону пула W2T4
  из CPU_BATCH_WORKERS_RESEARCH (раздел 11).
- B: 1×4/T1 ≡ 2×2/T1 ≡ 4×1/T1 (12/12, все прогоны).
- Fast INT8: fa1 ≡ fa2 (T4), fb1 ≡ fb2 (T1), 12/12.
- Правило подтверждено: WAV зависит от модели/точности/T/seed и НЕ
  зависит ни от числа процессов, ни от распределения Pocket.

Соответствие WAV исходным TXT проверено по именам (part_XX), дублей и
пропусков нет (claim-очередь, 12/12 в каждом прогоне), все процессы
завершились штатно (process_end в каждом журнале, exit 0), сирот нет.

## 5. Ответы на вопросы

1. **2×1 быстрее 1×2 при T=4?** Нет: Slow FP32 1.00×, Fast INT8 — 2×1 на
   2.9% медленнее.
2. **2×2 / 4×1 быстрее 1×4 при T=1?** Нет: 1.00× / 0.99×.
3. **CPU utilization?** Не растёт от многопроцессности (~45–49% от 8
   логических во всех конфигурациях) — CPU не является узким местом
   разделения; узкое место — сам граф/память.
4. **RAM/потоки/загрузка?** Peak Σ RAM одинаков или чуть выше (+0…12%);
   число потоков на процесс падает пропорционально, суммарно ~равно;
   стоимость загрузки моделей дублируется (каждый процесс грузит свои
   Pocket, ~1–2 с, параллельно).
5. **Throughput vs latency?** Neither: throughput одинаков, latency
   первого WAV одинакова (27.6–27.9 с A; 45.9–46.3 с B; 15.1–15.7 с fa).
6. **FP32 vs INT8?** Различий в поведении нет — INT8 просто быстрее и
   легче; паттерн «многопроцессность бесполезна» одинаков.
7. **Стоит ли поддерживать многопроцессный CPU batch в G6.6?** **Нет.**
   Устойчивое преимущество отсутствует (0%…−3%), а цена реальна:
   IPC/Job Object/watchdog (как в CUDA hybrid), дублирование RAM ORT,
   усложнение отмены и ошибок.

## 6. Рекомендации для G6.6

- **Архитектура**: один процесс, постоянный пул Pocket (механизм B из
  CPU_BATCH_WORKERS_RESEARCH), общая динамическая очередь файлов — ровно
  как `persistent.rs` уже делает для CUDA.
- **Производительность**: 4 Pocket × T=1 (максимум, 2.9 ГБ Slow FP32 /
  1.9 ГБ Fast INT8, латентность первого файла ~46 с); **баланс: 2 Pocket
  × T=4** (1.3–1.5 ГБ, 1.26–1.44× к GUI, первый файл ~28 с).
- **Auto**: 1 процесс всегда; W по правилу из CPU_BATCH_WORKERS_RESEARCH
  §11-Д (`clamp(1, logical/4, 4)` + лимит свободной RAM), T не менять
  (4).
- **Настройка «процессов» пользователю не нужна**; принцип выбора режима
  CPU/CUDA можно оставить общим (для CUDA гибрид 2×2 остаётся отдельным
  осознанным режимом — выводы CPU на CUDA не переносятся и обратно).

## 7. Ограничения

- n=1–2 на конфигурацию (бюджет 35 мин соблюдён, ~30 мин); разброс
  повторов ≤ ±1.5%, наблюдаемые различия (0–3%) меньше или сопоставимы с
  ним — вывод «нет преимущества» устойчив по направлению в 11 прогонах
  5 сравниваемых пар.
- Дополнительная проверка 1×4/T4 vs 2×2/T4 не выполнялась: этап B не
  показал перспективы многопроцессности (условие раздела 4 ТЗ).
- Slow INT8 не измерялся (приоритет по бюджету — Slow FP32 + Fast INT8;
  поведение INT8-паттерна подтверждено на Fast INT8).
- CPU-time ранних многопроцессных прогонов до фикса счётчика занижен
  (после фикса — достоверно); Peak Working Set не собирался (только
  Private Bytes — основной маркер).
- Один внешний выброс среды (A1, 722 с) исключён по правилу одного
  повтора.

## 8. Итог

**Многопроцессный CPU-пул не даёт преимуществ** (0…−3% к wall, утилизация
CPU не растёт, RAM не экономится) и не рекомендуется для G6.6. Выбор —
однопроцессный постоянный пул; число Pocket и T — по рекомендациям
`docs/CPU_BATCH_WORKERS_RESEARCH.md` §11. Production-код не менялся.
