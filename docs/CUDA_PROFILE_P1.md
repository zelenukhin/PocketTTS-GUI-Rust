# CUDA_PROFILE_P1 — диагностика отставания Rust-CUDA от Python (RTX 3060)

Дата: 2026-11-09. Стенд: RTX 3060 12 ГБ, драйвер 581.42, Windows (WDDM),
ORT 1.23.2 GPU-сборка (`deps/ort-gpu-wheel`), CUDA EP `use_tf32=0`, FP32,
модель ru-v2-slow (те же веса: Rust — ONNX `flow_lm_main.onnx` 302 МБ,
Python — PyTorch `model.safetensors` 438 МБ из
`C:\PocketTTS-GUI\PocketTTS-GUI\custom_models\Shtorm_PocketTTS_RU_v2_slow`).

## Главное открытие: сравниваются разные стеки исполнения

Python PocketTTS-GUI **не использует ONNX Runtime для синтеза** — это
PyTorch (`pocket_tts` 3.1.0, `TTSModel.load_model`, `model.to("cuda")`).
PyTorch держит веса и KV-кэш на GPU постоянно (кэш преаллоцируется NaN-ами
на весь чанк, `tts_model.py:_expand_kv_cache`), mimi-декодер работает в
**отдельном потоке параллельно** с генерацией (`_decode_audio_worker`), а
единственная синхронизация на кадр — `is_eos.item()`. Rust гоняет те же
веса через ONNX Runtime CUDA EP без I/O Binding: на каждый кадр полный
круг CPU→GPU→CPU всех state-тензоров через session.run.

Вывод P1: отставание — не «плохой GPU-код Rust», а архитектура привязки
ввода/вывода ORT-сессий. GPU при этом простаивает (~35–40% Load).

## 1. Честное сравнение: одинаковое задание

Текст: 13 чанков, речь 64.01 с (+6.00 с пауз = 70.01 с итог; длительности
совпали у обеих сторон до сотых). Голос `Василий Леванов F5-TTS3.wav`,
seed 42, temp 0.3, EOS −4/5/3 (teratts), decode_steps 1, anti_repeat,
brightness 8, denoise off, WAV. Python: 3 процесса (spawn,
`synthesis_process_entry`, как GUI); Rust: `synthesize --workers 3
--threads 4`. Драйвер и сырые данные: `out/cuda_p1/` (gpu-CSV, summary.json,
chunk-логи).

| Метрика | Python 3 proc (PyTorch) | Rust 3w (ORT CUDA) | 
|---|---:|---:|
| Загрузка моделей, с | 9.5 / 9.5 / 10.1 | ≈5 (в wall) |
| Синтез без загрузки, с | **8.66 / 8.82 / 9.35** | 25.3 (wall 30.5 − загрузка) |
| Полное задание, с | 19.1 / 19.1 / 20.5 | 30.7 / 30.3 / 30.4 |
| RTF синтеза (синтез/речь) | **0.135 / 0.138 / 0.146** | ≈0.40 |
| RTF полный (wall/итог 70.01 с) | 0.298 / 0.299 / 0.317 | 0.431 / 0.429 / 0.430 |
| Средний чанк (per-chunk gen), с | **1.81 / 1.84 / 1.93** | 6.20–6.25 |
| GPU Load средн./пик (окно синтеза) | 54–65% / 78–80% | 36–39% / 45–48% |
| VRAM всего (пик) | 3187–3195 МБ | 6941–6963 МБ |
| VRAM на инстанс | ≈ **+0.88 ГБ/процесс** | ≈ +2.09 ГБ/воркер |
| CPU средний (окно синтеза) | 71–81% | 57–65% |

Python синтезирует тот же текст **в ~2.9 раза быстрее** (8.9 с против 25.3 с)
и держит GPU в 1.6–2 раза занятее. Замеры GPU — поллинг nvidia-smi 0.9 с
(окно синтеза), что согласуется с наблюдениями GPU-Z пользователя
(80% против 42%).

## 2. Масштабирование воркеров Rust (CUDA, threads=4)

Одно и то же задание (13 чанков), 3 повтора (4w и 3×2t — 1 прогон);
VRAM до запуска 4w = 700 МБ (запас есть, прогон проведён).

| Воркеры | Wall, с | Σ времени чанков, с | Средний чанк, с | RTF wall | GPU avg/max | VRAM пик, МБ |
|---|---:|---:|---:|---:|---|---:|
| 1w×4t | 33.81/33.37/33.31 | 31.5–32.0 | 2.42–2.47 | 0.472–0.479 | 35–37% / ≤56 | 2844 |
| 2w×4t | 30.58/30.39/30.40 | 54.8–55.2 | 4.22–4.24 | 0.430–0.433 | 35–38% / 45–46 | ~4900 |
| 3w×4t | 30.71/30.32/30.35 | 80.6–81.2 | 6.20–6.25 | 0.429–0.431 | 36–39% / 45–48 | ~6950 |
| 4w×4t | 31.17 | 106.9 | 8.22 | 0.441 | 35% / 46 | 9012 |
| 3w×2t | 30.43 | 81.2 | 6.25 | 0.430 | 37% / 45 | 6941 |
| CPU 1w×4t (референс) | 48.40 | 47.3 | 3.64 | 0.691 | — | — |

Ключевые факты:

- **Время чанка растёт ЛИНЕЙНО с числом воркеров** (2.42→4.23→6.22→8.22 с):
  воркеры не параллелятся, а встают в общую очередь. Пропускная способность
  упирается в потолок ~70 с аудио за ~30 с при ≥2 воркерах; 4-й воркер
  только добавляет VRAM (+2.0 ГБ) и чуть ухудшает время.
- **GPU Load не растёт с воркерами** (35–39% при 1–4w) — общее место не GPU:
  это синхронные копии+WDDM+запуски ядер. Ответ на вопрос задания «почему
  +1.48–2.0 ГБ VRAM на воркера не дают нагрузки»: каждый воркер — 5 ORT-сессий
  со своими весами (≈437 МБ FP32), аренами/воркспейсами CUDA EP и staging
  стейтов; но исполнение остаётся связанным синхронными обменами, GPU
  простаивает.
- intra-op потоки CPU на CUDA-режиме не влияют (3w×2t ≡ 3w×4t).
- CUDA 1w быстрее CPU 1w всего в 1.44 раза (33.5 против 48.4 с) —
  при «чистых» ~14.6 мс GPU-работы на кадр должно быть в ~2.5 раза быстрее.

## 3. Разбивка времени по компонентам (SHTORM_PHASE_TIMING=1)

Чанк 1 (68 кадров), медиана по 13 чанкам того же порядка:

| Фаза | 1 воркер | 3 воркера |
|---|---:|---:|
| prep (BPE+text-сессия) | 0.8 мс | 9.8 мс |
| voice (кэш) | 0.2 мс | 0.2 мс |
| prefix (2 прогона main) | 78 мс | 207 мс |
| сборка входных тензоров кадра | 1.0 мс | 1.4 мс |
| **main session.run (68 кадров)** | **2296 мс (33.8 мс/кадр)** | **4851 мс (71.3 мс/кадр)** |
| извлечение выводов main (to_vec) | 0.5 мс | 0.7 мс |
| noise (RNG) | 0.1 мс | 0.2 мс |
| flow session.run (68 кадров) | 108 мс (1.6 мс/кадр) | 1484 мс (21.8 мс/кадр) |
| decoder run (5 вызовов) | 81 мс | 347 мс |

- **main_run = ~93% времени генерации** (2296 из 2466 мс на чанк при 1w).
- При 3 воркерах main_run растёт ×2.1, а крошечный flow (39 МБ, чистый
  Gemm, 100% CUDA-узлов) — **×13** (1.6→21.8 мс/кадр): это время ожидания
  в очереди общих синхронных обменов, а не вычислений.
- Извлечение результатов (`try_extract_tensor().to_vec()`), сборка тензоров
  и RNG — пренебрежимо малы (<0.1% на чанк): гипотеза «виноваты лишние
  Vec-копии в Rust-коде» измерением НЕ подтвердилась.

## 4. CPU↔GPU копирования и настоящее GPU-время (ORT Chrome-trace)

Трейс одной фразы (73 прогона flow_lm_main, `out/cuda_p1/ep_traces`,
разбор `out/cuda_p1/parse_trace*.py`):

| Величина | Значение |
|---|---:|
| Wall session.run (без профилировщика, фаза-таймеры) | 33.8 мс/кадр |
| GPU kernel+memcpy время (события `*_kernel_time`) | **14.6 мс/кадр** |
| — из них вычисления | 13.86 мс/кадр |
| — из них device-memcpy | 0.71 мс/кадр |
| CPU-время узлов CPU-EP | 3.2 мс/кадр |
| CPU-время узлов CUDA-EP (launch+ожидание) | 11.4 мс/кадр |

- **57% wall-времени кадра — не GPU-работа**: синхронные обмены, запуск
  ~500 мелких ядер, исполнение shape-узлов на CPU. Отсюда GPU Load ~40%
  даже в один воркер (14.6/33.8 ≈ 43% заполнения).
- Стейты main-графа: 18 входов/18 выходов, из них 12 × [1,1000,16,64] f32
  = **49.2 МБ в одну сторону** → **~98 МБ PCIe на каждый 80-мс кадр**
  (1.23 ГБ/с на воркер при 12.5 кадр/с). Копии синхронные (сессия без
  I/O Binding), каждая пара воркеров делит этот путь — отсюда линейное
  замедление чанков и потолок пропускной способности.
- Пиковой нагрузки на PCIe по полосе нет (utilization.memory 6–13%) —
  узкое место не пропускная способность, а синхронность и латентность
  round-trip на кадр.

## 5. CPU-fallback узлы (подтверждение CUDA_FEASIBILITY)

Все вычислительные узлы (Gemm/MatMul/Conv) — на CUDAExecutionProvider.
На CPU остаются только shape/служебные операции main-графа: **16 206
событий узлов на фразу ≈ 222 узла на кадр**: Unsqueeze×3504, Gather×3504,
Cast×1752, Concat×2628, Slice×438, Reshape×438, Add/Mul/Div/Equal/Where/
Reciprocal/Sqrt (по 438–876). Они дают 3.2 мс CPU-времени на кадр и,
главное, заставляют ORT вставлять синхронизации CPU↔CUDA между EP.
mimi_encoder/decoder — та же картина (68–79% узлов на CUDA, остальное —
shape-операции). «Молчаливого падения всего графа на CPU» нет.

## 6. Три главных узких места (по измеренному влиянию)

1. **Синхронный покадровый круг CPU↔GPU всех стейтов main-сессии**
   (98 МБ/кадр; 57% wall вне GPU; полная сериализация воркеров — время
   чанка ×N при N воркерах). Устраняется I/O Binding/резидентными
   GPU-буферами стейтов: питоновский эквивалент (стейты постоянно на GPU)
   даёт 0.135 RTF на этом же железе.
2. **222 CPU-EP shape-узла на кадр в main-графе** (+пары синхронизаций
   CPU↔CUDA между провайдерами; 3.2 мс CPU + разрывы конвейера). Лечится
   на уровне экспорта графа (вынести shape-логику на GPU/свернуть), в
   рамках ORT-Rust — только частично.
3. **Отсутствие конвейеризации декодера и мелкие сессии в цикле**:
   mimi-decoder выполняется после всей генерации чанка (Python перекрывает
   его потоком; у Rust +65–105 мс/чанк), а flow — отдельный session.run
   на кадр с 4 крошечными входами (при 3w деградирует ×13 — общая очередь).
   Второстепенно против №1–2, но станет заметно после I/O Binding.

## 7. Рекомендация CUDA-P2: I/O Binding + резидентные стейты main/flow

Файлы: `crates/shtorm-engine/src/pocket.rs` (`States` → device-резидентный
двойной буфер), при необходимости новый модуль `gpu_states.rs`; проверка —
`bench`/`synthesize` до-после на этом же стенде (`out/cuda_p1` методика).

Архитектура:
- Для main-сессии (и затем flow) создать `IoBinding`: 18 стейтов как
  GPU-OrtValues ping-pong (выход кадра k = вход кадра k+1, без хост-копии);
  sequence/text_embeddings — предвыделенные GPU-буферы (заполнение
  `cudaMemcpyAsync` только при смене чанка/префикса);
- с хоста на кадр читается только `eos_logit` (4 Б, аналог `.item()` в
  Python) — семантика EosGate не меняется; `cond` остаётся на GPU как
  вход flow (flow тоже с I/O Binding);
- CPU-путь (Device::Cpu) не трогается; гибрид main/flow=CUDA +
  encoder/text/decoder=CPU — запасной вариант P2b, если io_binding в
  ort 2.0.0-rc.11 окажется непригоден.

Ожидаемая выгода (по измерениям): main_run 33.8 → ~15–17 мс/кадр
(GPU-bound), чанк 2.42 → ~1.3 с, RTF 1w 0.49 → ~0.26–0.30; воркеры
перестают сериализоваться на копиях и масштабируются до заполнения GPU
(ориентир Python: RTF 0.10–0.15 на 3 инстансах). VRAM: резидентные стейты
+49×2 МБ/воркер, staging-арены должны сократиться.

CUDA Graphs для main-графа — отдельный этап после I/O Binding: сейчас
динамические формы (растущая длина последовательности, скалярные offset-
стейты) делают захват графа нетривиальным; сначала фиксируется базовая
резидентность.

## 8. Риски для детерминизма и качества

- I/O Binding не меняет набор/порядок ядер внутри прогона — ожидается
  побитовый паритет CUDA до/после; обязательная проверка: WAV SHA256
  1w≡2w≡до-оптимизации на фикс. seed (методика — как в этом P1:
  `5ca845c0…` на тестовом тексте).
- CPU-режим не затрагивается вовсе (Device::Cpu без io_binding).
- EOS/anti_repeat/seed/temperature/decode_steps не изменяются; чтение
  eos_logit остаётся покадровым.
- Главный технический риск — зрелость io_binding CUDA в ort 2.0.0-rc.11
  (_lifetime device-буферов, синхронизация stream). Отсюда P2b-запасной
  план и требование «маленькими проверяемыми шагами».
- Качество аудио не зависит от транспорта тензоров (те же веса, те же
  ядра); риск только в ошибках реализации — ловится побитовым сравнением.
