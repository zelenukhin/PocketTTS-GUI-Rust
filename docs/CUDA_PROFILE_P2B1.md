# CUDA_PROFILE_P2B1 — независимые процессы Rust против нескольких CUDA-воркеров

Дата: 2026-11-10. Фактический HEAD: `ad232ecc7621da7f298e3f76284b7d1c4fe99e31`
(`ad232ec`, docs G5.2). Рабочее дерево до экспериментов: чистое, кроме
untracked `out/` (диагностика прошлых этапов). Исходники Rust, GUI,
Python-проект, модели и портативные комплекты **не изменялись**.

Стенд: Windows 10 x64 19045, Intel Core i7-6700K (4 ядра / 8 логических,
4.0 ГГц), NVIDIA RTX 3060 12 ГБ (драйвер 581.42, WDDM), ONNX Runtime
1.23.2 (`deps/portable`, CUDA EP), Rust `ort` 2.0.0-rc.11 (dynamic load),
модель Shtorm-PocketTTS-RU v2 slow (FP32, TF32=0), CUDA I/O Binding
включён (обычный путь, `SHTORM_CUDA_IO_BINDING` не задана).

## 0. Итог

**Нет: несколько независимых процессов Rust не масштабируются лучше, чем
несколько CUDA-воркеров в одном процессе — они масштабируются практически
так же, а по эффективности GPU чуть хуже.**

- 1 → 2 независимых процесса: совокупный throughput **+17%**
  (8.34 → 9.76 с речи за секунду синтеза).
- 1 → 3 независимых процесса: **+21%** (8.34 → 10.05); третий процесс
  даёт только +3% и стоит ещё ~2.1 ГБ VRAM.
- 1 → 2 → 3 воркера в одном процессе: **+14% → +18%**
  (7.76 → 6.78 → 6.60 с окна синтеза на то же задание).
- Время чанка растёт одинаково в обоих случаях: 0.62 → 1.04 → 1.50 с
  (процессы) и 0.62 → 1.08 → 1.60 с (воркеры). `main.run` на кадр:
  6.0 → 11.2 → 16.5 мс (процессы) и 6.0 → 10.7 → 15.6 мс (воркеры).
- GPU Load растёт (42 → 72 → 80%), но полезная работа — почти нет
  (Scenario C: «GPU Load растёт, throughput не растёт»).
- Отдельные процессы **увеличивают** время GPU-работы на одно и то же
  задание на 58% (3.22 → 5.09 с GPU-busy на текст), тогда как воркеры
  одного процесса держат его постоянным (3.31 → 3.08 → 3.16 с). Это
  согласуется с накладными расходами смены CUDA-контекстов/WDDM между
  процессами; внутри одного процесса сессии делят контекст дешевле.

Причина не в «одном процессе ONNX Runtime»: три процесса с независимыми
ORT-сессиями, CUDA EP и потоками ведут себя как три воркера одного
процесса. Причина глубже — покадровая латентность графа (**≈540
CUDA-ядер + 222 CPU-узла + межEP-синхронизации на кадр**, ~57% времени
GPU простаивает даже при 1 воркере) и накладные расходы межпроцессной
конкуренции CUDA-контекстов. Многопроцессный режим GUI смысла не имеет.
CUDA-P2B.2 должен оптимизировать покадровый путь ORT/CUDA, а не добавлять
параллелизм.

### 2.2. Запуск

Launcher: `tools/bench-cuda-multiprocess.ps1` (новый, только диагностика).
Он запускает N процессов через `.NET Process` с асинхронным чтением
stdout/stderr (таймстемпы строк с точностью опроса ~25 мс), сам запускает
мониторы и завершает только собственные PID. Команды:

```powershell
# A: независимые процессы, по 1 воркеру
powershell -NoProfile -ExecutionPolicy Bypass -File tools\bench-cuda-multiprocess.ps1 -Label a1 -Processes 1 -Workers 1 -Reps 3
powershell ... -Label a2 -Processes 2 -Workers 1 -Reps 3
powershell ... -Label a3 -Processes 3 -Workers 1 -Reps 3
# B: один процесс, 1/2/3 воркера
powershell ... -Label b1 -Processes 1 -Workers 1 -Reps 3
powershell ... -Label b2 -Processes 1 -Workers 2 -Reps 3
powershell ... -Label b3 -Processes 1 -Workers 3 -Reps 3
# C: три задания последовательно
powershell ... -Label c_seq -Processes 3 -Workers 1 -Sequential -SkipWarmup -Reps 2
# диагностика CPU-потоков
powershell ... -Label a3_t2 -Processes 3 -Workers 1 -Threads 2 -SkipWarmup -Reps 1
powershell ... -Label a3_t1 -Processes 3 -Workers 1 -Threads 1 -SkipWarmup -Reps 1
```

Фактический аргумент каждого процесса (пример для A3):

```
target\release\synthesize.exe
  --model-dir C:/Users/alexa/Downloads/pocket_tts_android/build/onnx/ru-v2-slow
  --voice "C:/PocketTTS-GUI/examples/Василий Леванов F5-TTS3.wav"
  --text-file <repo>/out/cuda_p1/test_text.txt
  --out <run>/pN/out.wav --format wav --device cuda --workers 1
  --threads 4 --seed 42 --char-rules "<...>/runtime.json" --chunk-log
```

Окружение: `PATH=<repo>/deps/portable;...`,
`ORT_DYLIB_PATH=<repo>/deps/portable/onnxruntime.dll`,
`SHTORM_PHASE_TIMING=1`, `SHTORM_CUDA_IO_BINDING` снята (auto → CUDA I/O
Binding), `SHTORM_TEST_CANCEL_AFTER_MS` снята.

Мониторы: `tools/bench-cuda-gpu-monitor.ps1` — nvidia-smi loop 100 мс
(util.gpu, util.memory = Memory Controller Load, VRAM, power, SM clock,
P-state) + `nvidia-smi dmon -s t` 1 с (PCIe Rx/Tx); CPU —
`tools/bench-cuda-cpu-sampler.ps1` (~1.3 с на сэмпл из-за стоимости WMI).
Фоновый baseline отдельно: GPU 17.8% avg / 20% max, Memory Controller
5.3%, VRAM 598–612 МБ (DWM/оверлей NVIDIA/медиаплеер; чужие процессы не
трогались).

### 2.3. Синхронизация процессов и определение окон

Барьера после загрузки моделей нет. Вместо него launcher фиксирует
таймстемпы строк:

- `load <graph>: N ms` — загрузка каждой из 5 сессий;
- `CUDA-P2A: io binding active` — движок реально готов (после
  `IoStates::new`, ~0.5 с);
- `[k/13] готов` — завершение чанка;
- `файл: ...` — конец генерации/публикации.

Окно синтеза процесса = от `io binding active` (первый готовый движок;
для B — первый из воркеров) до строки `файл:`. Загрузка моделей в окно
не входит. Групповое wall-время включает загрузку/старт и приводится
отдельно.

Отсутствие барьера не исказило перекрытие: в A2 старты процессов
разошлись на 1–7 мс, в A3 — на 32–64 мс; время одновременного синтеза
всех трёх процессов 18.66–19.01 с при union 18.99–19.18 с (98–99%).
Загрузка моделей симметрична (движок готов через ~2.8–2.9 с после
старта), поэтому отдельный barrier для этой нагрузки не требовался.
Это проверено измерением, а не предположением.

## 8. VRAM, CPU, PCIe, питание

- VRAM пик: A1 2.75 ГБ, A2 4.90 ГБ (2.45/процесс), A3 7.05 ГБ
  (2.35/процесс); B2 4.83 ГБ, B3 6.87 ГБ. Baseline 598–612 МБ; запас

- CPU avg в окне синтеза: A1 39%, A2 55%, A3 69%; B1 39%, B2 51%,

- Memory Controller Load: A1 21.4%, A2 26.9%, A3 28.2%; GPU util в B
  42.6–47.9%. Далеко от насыщения. SM clock 1925–1935 МГц, P-state P2;
  питание 65–67 Вт (A1), 75–76 Вт (A2/A3) при TDP 170 Вт.
  Термотроттлинга нет.
- PCIe: Rx/Tx 441/383 (A1), 509/351 (A2), 501/361 МБ/с (A3) по dmon
  1 с; фон Tx ~226 МБ/с. Полоса PCIe 3.0 x16 (~12 ГБ/с) не является
  ограничением; I/O Binding оставляет на кадр только 128 Б H2D и
  4.1 КиБ D2H, плюс 46.9 МиБ нулей на чанк.
- Python VRAM: 1.49/2.37/3.24 ГБ для 1/2/3 процессов, 3.23 ГБ для трёх
  независимых.

## 10. Погрешность и фон

- Разброс окон синтеза по 3 повторам: A1 ±0.02 с (0.3%), A2 ±0.05
  (0.4%), A3 ±0.10 (0.5%), B1 ±0.09 (1.2%), B2 ±0.07 (1.0%), B3 ±0.05
  (0.8%). Python ±0.1 (1%). Выводы (+17/+21% и 1.14/1.18×) многократно
  больше разброса.
- GPU util шумит сильнее (A1 37.6–47.2% при среднем 41.9): окно короткое
  (7.7 с), а фон (DWM/оверлей NVIDIA/медиаплеер) даёт 17.8% avg / 20%
  max в простое. Поэтому абсолютный GPU Load сравнивается с этим
  baseline, а главная метрика — секунды речи на секунду синтеза.
- Сэмплирование: GPU 100 мс (nvidia-smi loop), PCIe 1 с (dmon), CPU
  ~1.3 с (WMI); GPU max — мгновенный пик, не устойчивое значение.
- Фон стабилен между сериями (VRAM 598–612 МБ, CPU 20–40% в простое),
  чужие процессы не завершались. Модель/драйвер/ORT не менялись.
- Загрузка моделей исключена из окон синтеза; group wall включает её и
  приводится отдельно. Барьер не использовался, но старты A2/A3
  разошлись на ≤64 мс, а одновременность — 98–99% (§2.3).
- Ограничение: точное GPU-время по Nsight/CUPTI на этой машине
  недоступно (P2A: nsys «Connection to Agent lost»), поэтому GPU-busy —
  это util × wall по nvidia-smi, а не CUPTI-длительности ядер.

## 11. Подтверждённые причины плохого масштабирования

1. **Не границы процесса и не общий объект ONNX Runtime.** Три
   независимых процесса с разными ORT-сессиями, CUDA EP и потоками
   дают ту же картину, что три воркера одного процесса: чанк 1.50/1.60 с,
   main 16.5/15.6 мс/кадр, выигрыш +21/+18%. Глобальный mutex/общий
   stream ORT внутри процесса не может объяснить межпроцессное поведение.
2. **Не intra-op потоки CPU.** `--threads 1/2/4` в A3 дают 22.27/22.25/
   22.14 с и одинаковый main.run; потоковый пул не является узким местом.
3. **Не GPU-вычисления, не память, не PCIe, не VRAM.** Питание 65–76 Вт
   из 170, Memory Controller 21–28%, SM clock максимальный, PCIe
   <1 ГБ/с, VRAM 7.05/12 ГБ без paging. GPU не насыщен.
4. **Не загрузка моделей и не рассинхронизация старта.** Загрузка
   1.4–2.2 с на процесс, движок готов через 2.8–2.9 с; старты A3 в
   пределах 62 мс; окна синтеза измерены отдельно от загрузки.
5. **Покадровая латентность графа.** По трассировке P2A на кадр
   приходится ≈540 CUDA-ядер и 222 CPU-EP узла (Unsqueeze/Gather/Cast/
   Concat/Slice/Reshape и арифметика форм) плюс межEP-синхронизации.
   При 1 воркере GPU занят ~3.2 с из 7.7 с (42%), т.е. ~58% времени —
   простой на CPU-диспетчеризацию, синхронизации и запуск мелких ядер.
   Добавление воркеров/процессов заполняет часть простоев, но каждый
   участник замедляется почти пропорционально, поэтому суммарный
   выигрыш 18–21%, а не 2–3×. Это классический latency-bound профиль,
   а не throughput-bound.
6. **Межпроцессная конкуренция CUDA-контекстов (WDDM).** GPU-busy на
   одно и то же задание растёт только между процессами (+58%),
   а между воркерами одного процесса — нет (±5%). Внутри процесса
   несколько сессий делят CUDA-контекст процесса и переключаются
   дешевле, чем отдельные контексты процессов под WDDM. Python с более
   крупными ядрами платит за межпроцессную конкуренцию меньше (~+10%
   GPU-busy на текст), но тоже не получает 3× (1.82× на трёх процессах,
   GPU 66%). Это согласуется с известным поведением WDDM на GeForce:
   контексты time-slice'ятся, а не выполняются одновременно.

## 12. Оставшиеся непроверенные гипотезы

- Точное разделение вклада CPU-диспетчеризации ORT и GPU context switch
  не измерено: Nsight/CUPTI недоступны (P2A). Оценка «WDDM» — наиболее
  согласованная с данными, но не единственная логически возможная.
- `use_ep_level_unified_stream`, `session.use_env_allocators`,
  `arena_extend_strategy`, `enable_mem_pattern`, CUDA Graph
  (`enable_cuda_graph`) в этой серии не включались. Внутрипроцессный
  выигрыш от них возможен, но межпроцессное масштабирование они не
  исправят.
- CUDA Graphs для main-графа: per-frame формы постоянны
  (`sequence [1,1,32]`, `text_embeddings [1,0,1024]`, состояния
  фиксированы), но 222 CPU-узла, вероятно, делают захват
  неработоспособным без переэкспорта. Не проверялось.
- Переэкспорт main без CPU-fallback узлов (shape-операции на GPU) —
  главный кандидат P2B.2; в P2B.1 запрещён (модели не менялись).
- Поведение на Linux/TCC и CUDA MPS: на GeForce/Windows MPS недоступен,
  TCC на GeForce не включается; выводы относятся к WDDM-стенду.
- Внутренние блокировки ORT не аудировались построчно; их роль как
  главной причины исключена межпроцессной эквивалентностью, но
  остаточный вклад в покадровую латентность не измерен.

## 13. Рекомендация по архитектуре и CUDA-P2B.2

**Многопроцессный пул в GUI не внедрять.** Максимум +21% throughput за
2.6× VRAM (7.05 ГБ), 3× работу загрузки моделей и усложнение IPC/отмены/
порядка; 2-й процесс даёт +17%, 3-й +3%. Внутрипроцессные 2 воркера дают
+14% при том же порядке VRAM (4.8 ГБ) и без IPC — если нужен запас, это
единственный оправданный вариант; 3-й воркер не нужен.

**CUDA-P2B.2 — оптимизация реального узкого места, а не параллелизм.**
Приоритеты:

1. **Убрать 222 CPU-EP узла/кадр и межEP-синхронизации** в main-графе
   (переэкспорт с shape-операциями на CUDA/статическими формами либо
   эквивалентная оптимизация графа). Это должно снять ~3 мс/кадр
   не-GPU времени и поднять util одного воркера. Главный кандидат.
2. **Сократить ~540 запусков ядер/кадр**: фьюзинг/оптимизатор графа,
   затем — оценка ORT CUDA Graph с постоянными per-frame формами
   (prefix/decoder вне графа). Без шага 1 захват, вероятно, невозможен.
3. **Малые пункты**: I/O Binding для flow/decoder (убрать 4 КиБ D2H и
   копийный цикл), `use_ep_level_unified_stream`, настройки арен;
   ожидаемый выигрыш меньше, но дешёв в проверке.
4. Мерить тем же стендом A1/B1 (13 чанков, WAV SHA256, main.run/чанк);
   цель — чанк 0.62 → ~0.45–0.5 с при 1 воркере (снятие ~3–4 мс/кадр),
   без изменения seed/EOS/FP32/TF32 и с побитовым WAV-паритетом.

Ожидание: если шаг 1 уберёт ~3 мс/кадр, один воркер приблизится к
GPU-bound режиму, и необходимость в нескольких воркерах/процессах
исчезнет. Параллелизм — следствие, а не лекарство: текущий потолок
задан покадровой латентностью и WDDM, а не числом воркеров.
