## 0. Итог

**Несколько независимых процессов не быстрее постоянного пула воркеров одного
процесса — они чуть медленнее, дороже по VRAM и тратят заметно больше
GPU-времени на ту же работу.**

- Постоянный пул (модель загружается один раз) ускоряет три файла на
  **7.6%** относительно трёх последовательных одиночных запусков
  (54.40 → 50.29 с cold wall). Весь выигрыш — две сэкономленные загрузки
  модели (2 × 1.4 с) и два запуска процесса; сам синтез не меняется
  (629 мс/чанк в обоих случаях).
- 1 → 2 воркера: **+12.4%** throughput на пакете из 3 файлов (1.12× wall),
  в установившемся режиме длинной очереди — **+33%**. VRAM 2.74 → 4.84 ГБ.
- 2 → 3 воркера: **+5.0%** на трёх файлах, а в установившемся режиме
  **−7%** относительно двух воркеров (1.24× против 1.33×) за +2.1 ГБ VRAM.
  Третий воркер не нужен.
- Два/три **процесса** против двух/трёх **воркеров** одного процесса:
  одинаковый объём работы, но процессы на **0.8–1.2% медленнее** по wall,
  тратят **+39%/+72%** GPU-busy-времени, +2.2%/+3.1% VRAM и +5.5%/+7.2%
  `main.run` на кадр.
- Переиспользование модели подтверждено фактами: ровно 1/2/3 загрузки
  `Pocket` (5/10/15 ONNX-сессий) на пакет, переход между файлами
  0.0–1.0 мс, все **72/72** WAV побитово равны эталону одиночного запуска,
  включая повторный файл на уже прогретом `Pocket`.

Рекомендация для пакетной обработки аудиокниг: **один процесс, постоянный
пул, 2 воркера** (4.8 ГБ) — против текущего поведения GUI (пул на каждый
файл) это **−16.7% wall** и **+20%** throughput на трёх файлах, а на длинной
очереди до **+33%**; 3 воркера не брать.

## 1. «Блокер NAS» из P2B.1 оказался ошибкой скрипта

диска (`C:\DISKSTATION\...`), а не как UNC — `Test-Path` всегда `false`.
Дополнительно сам вызов из bash терял один слэш при двойном экранировании.
С корректным `\\DISKSTATION\Ableton 2\Temp2` шара **доступна**: в каталоге
лежат архивы предыдущих этапов вплоть до `full-1e4603d-20261110-040125.zip`.

**Следствие:** блокер снят, бэкап HEAD создан штатной процедурой
(`out/backup_full_head.ps1`, 148/148 blob + SHA256), и диагностический
runner на этом этапе реализован полноценно. Скрипт `out/nas_check.ps1`

## 4. Что именно сравнивалось

Общее для A и B (обеспечено кодом, а не договорённостью):

- каждый воркер = свой `Pocket` + свои ONNX-сессии, созданные **один раз**
  до первого файла и живущие до конца пакета; `Pocket` освобождается только
  после последнего файла;
- **один файл обрабатывается одним воркером целиком** (чанки файла не
  распределяются между воркерами) — `run_job` с `workers = 1`;
- конвейер файла — как в `pipeline::synthesize_stream`: `chunk_pipeline` →
  `to_model_stress_notation` → `apply_char_rules` → `chunk_pause_s` →
  `RealWorker` (покой + DSP) → `WavSink` → `publish`; seed+index
  сбрасываются на каждом файле (индексы 0..N−1, base_seed 42);
- одинаковые ORT/CUDA-настройки, один и тот же WAV-голос, один и тот же
  `runtime.json`; WAV PCM16.

Различаются режимы **только границами процессов**:

| | A (`pool`) | B (`process`) |
|---|---|---|
| Процессов | 1 | N |
| Воркеров в процессе | N | 1 |
| Очередь файлов | `AtomicUsize` в памяти | claim-локи (`create_new`) в общем каталоге |
| Кто берёт следующий файл | свободный воркер | свободный процесс |

Инструмент: новый диагностический бинарь
`crates/app-core/src/bin/diag_p2b2.rs` (subcommand'ы `analyze`, `split`,
`pool`, `process`). Он не подключён к GUI и не меняет обычный алгоритм
пакетного режима; математика синтеза не дублируется — используется
`RealWorker`/`Pocket`/`WavSink` из `app-core`. `run_job` вызывается с
фабрикой, которая «одалживает» постоянный воркер у пула на время файла
(`Loaned`: на `Drop` возвращает `Pocket` в слот), поэтому работают все
штатные механизмы пула (порядок, backpressure, отмена, `catch_unwind`),
а модель переживает файл.

Сопоставимость, которую требовало задание: ни один режим не повторяет
загрузку модели на файл, ни один не дробит файл между воркерами, постобработка
(DSP, паузы, WAV) и настройки ORT/CUDA идентичны — различаются только
границы процессов.

## 5. Методика

- 3 текстовых файла; в каждом прогоне каждый файл синтезируется целиком.
- Для каждого режима: **1 прогрев** (в статистику не входит) + **3
  измеренных повтора**; каждый повтор — новый процесс(ы), новые уникальные
  каталоги вывода, новые WAV (`create_new`, без перезаписи).
- Порядок чередовался между повторами, чтобы дрейф фона/температуры не
  приписывался режиму: прогрев A→B, r1 A→B, r2 B→A, r3 A→B со сдвигом.
- Cold wall — от старта процесса(ов) до последнего выхода (включая загрузку
  модели). Warm wall — от готовности **всех** воркеров до конца последнего
  файла. Чанк/файл/загрузка/переход — из событий самого runner'а
  (`events_p*.jsonl`: `worker_ready`, `file_claim`, `file_done`,
  `worker_release`, `process_end`; монотонное время процесса + UTC-метки).
- Мониторы те же, что в P2B.1: `tools/bench-cuda-gpu-monitor.ps1`
  (nvidia-smi, 100 мс; PCIe 1 с) и `tools/bench-cuda-cpu-sampler.ps1`
  (CPU ~0.5–1.3 с). Окна GPU/CPU — warm-окно; базовая линия — сэмплы до
  старта процесса.
- `main.run` мс/кадр — из строк `phase | chunk …` (`SHTORM_PHASE_TIMING=1`).
- Проверка кодов завершения: `rc` каждого процесса = 0 во всех 24 прогонах;
  таймаутов нет.
- Эталон одиночного запуска: по одному `synthesize.exe` на файл,
  последовательно (3 процесса, 3 загрузки модели) — два независимых прогона.

  загружаются параллельно и конкурируют за диск/GPU/CPU; общий wall загрузки
  ≈ время одной загрузки.
- reuse=0 в A3/B3 — это не пересоздание, а следствие «3 файла / 3 воркера»:
  каждый файл законно попадает на свой свежий `Pocket`.
- **Повторная обработка на том же `Pocket`** (`--repeat-first`): после
  файлов 1–3 первый файл синтезирован ещё раз в том же процессе и на том же
  `Pocket` — WAV **побитово равен** эталону одиночного запуска
  (`aeb42c99…`, 6 034 124 байта, 125.71 с), переход к нему 0 мс, загрузок
  по-прежнему 1 `Pocket` / 5 сессий. Значит, состояние модели, кэш голосовых
  embeddings и прочие кэши **не переносятся** между файлами: результат
  зависит только от seed+индекса чанка и параметров.

## 14. Ответы на вопросы задания

**1. Насколько постоянный пул ускоряет три файла относительно трёх
последовательных отдельных запусков?**
На **7.6%** по cold wall: 54.40 → 50.29 с (1.08×); по warm-работе
48.53 против 54.40 с (1.12×). Выигрыш целиком из накладных расходов —
две сэкономленные загрузки `Pocket` (2 × ≈1.4 с) и два запуска
процесса/ORT (≈1.2 с). Сам синтез идентичен: 629 мс/чанк в обоих случаях.
С тремя воркерами постоянный пул даёт 1.25× (43.52 с, −20%).

**2. Даёт ли два воркера заметный выигрыш?**
Да. +12.4% throughput на пакете из трёх файлов (48.53 → 43.19 с warm,
1.12× wall), и это воспроизводимо (разброс 0.7%). Причина «всего» +12%, а
не +33%: на трёх файлах с двумя воркерами один воркер получает два файла и
становится критическим путём. В установившемся режиме длинной очереди
выигрыш **+33%** (2 × 629/945). Цена — +2.1 ГБ VRAM.

**3. Даёт ли третий воркер полезный прирост?**
Почти нет. На трёх файлах +5.0% к двум воркерам (43.19 → 41.14 с), а в
установившемся режиме **хуже** двух (1.24× против 1.33×): время чанка растёт
сильнее, чем добавляется воркеров (630 → 945 → 1520 мс). За +2.1 ГБ VRAM
(6.94 ГБ) — не рекомендуется.

**4. Лучше ли два/три отдельных процесса, чем два/три воркера одного
процесса?**
Нет. По wall они равны в пределах шума, причём процессы **немного хуже**:
A2 43.19 против B2 43.71 с (−1.2% в пользу одного процесса), A3 41.14 против
B3 41.47 с (−0.8%). При этом B тратит существенно больше GPU-времени на ту же
работу (GPU-busy 27.8 против 20.0 с; 32.8 против 19.1 с), держит более
высокий util (63.6/79.1% против 46.2/46.4%), больше VRAM (+2.2%/+3.1%) и
более медленный `main.run` (+5.5%/+7.2%). Архитектурных преимуществ у
процессов нет: та же пропускная способность, хуже эффективность.

**5. Какой вариант экономичнее по VRAM?**
Один процесс с N воркерами: 2.74 ГБ (N=1, столько же), 4.84 против 4.95 ГБ
(N=2), 6.94 против 7.15 ГБ (N=3) — на 2.2–3.1% меньше, чем N процессов.
Стоимость воркера/процесса ≈ 2.1–2.3 ГБ; разница — общий CUDA-контекст и
один рантайм ORT на процесс.

**6. Что предпочтительно для длинной пакетной обработки аудиокниг?**
Один процесс с **постоянным** пулом и **2 воркерами**: модель загружается
один раз за пакет, файл не дробится между воркерами, очередь общая, переход
между файлами ≈ 0 мс. Это +33% throughput против одного воркера в
установившемся режиме и −16.7% wall против текущего поведения GUI
(пул создаётся заново на каждый файл: 54.40 → 45.29 с). Для VRAM-стеснённых
условий или при общей GPU — 1 воркер (2.75 ГБ), потеряв ~25% throughput.
Третий воркер не брать.

## 15. Ограничения

- Измерялся пакет из трёх файлов; относительный выигрыш N воркеров на
  длинной очереди оценён формулой N × (t1/tN) по времени чанка, а не прямым
  замером на 10–20 файлах. Оценка согласуется с измеренным на трёх файлах.
- `diag_p2b2` — диагностический инструмент: он вызывает `run_job` с
  `workers = 1` на файл и не проверяет GUI-специфичные пути (фазы
  публикации, ffmpeg-синки). Математика синтеза и WAV-вывод общие с
  `synthesize.exe`, паритет SHA256 это подтверждает.
- Пул между файлами в GUI пока не переиспользуется (`docs/G3_BATCH.md`);
  этот этап показал эффект, но не внедрял его (§16 — не входит в задание).
- Точные CUDA-синхронизации и context switches не измерены (нет Nsight/CUPTI).
- Максимум 3 воркера/процесса по политике VRAM; 4-й не проверялся.
- Десктоп не изолирован: фон GPU 2–12%, CPU 15–50%, VRAM ≈ 537 МБ; порядок
  A/B чередовался, чтобы это не приписывалось режиму.
- Denoise выключен (как в P2B.1), decode_steps = 1, FP32/TF32=0 — выводы
  относятся к этому профилю.

## 16. Рекомендация

1. **Не внедрять многопроцессный режим** — ни выигрыша по времени, ни
   экономии VRAM; только IPC, отмена и порядок усложняются.
2. **Внедрять переиспользование пула между файлами пакета** (это следующий
   очевидный шаг, но отдельным заданием): одна загрузка модели на пакет,
   1–2 воркера, сброс seed/индекса на каждом файле. Ожидаемый эффект:
   −7.6% wall при 1 воркере, −16.7% при 2 воркерах (54.40 → 45.29 с на
   трёх файлах), до +33% на длинной очереди.
3. **CUDA-P2B.2 по существу (покадровый путь ORT/CUDA)** остаётся главным
   резервом: 630 мс/чанк при 1 воркере и util ≈ 42% — это по-прежнему
   latency-bound, а не throughput-bound; параллелизм лишь заполняет простои
   и упирается в 1.33×.
