# G3 — безопасный пакетный режим (2026-11-09)

## G3.1 — исправления по замечаниям (2026-11-09)

- **Физическая безопасность путей**: `ensure_no_reparse_components` проверяет
  все существующие компоненты выходного пути (symlink, junction, любой
  reparse point) и отказывает с понятной диагностикой; по таким путям
  приложение не переходит автоматически. `physical_path` / `physically_under` /
  `physically_same` сравнивают пути через canonicalize существующего префикса
  (component-wise, без учёта регистра на Windows), поэтому выходная папка,
  заданная альтернативным путём или через junction, распознаётся как
  совпадающая/вложенная. Обход источника пропускает каталоги-ссылки.
- **Отмена пакета**: в `BatchReport` добавлен явный флаг `cancelled`, который
  не выводится из статусов файлов. Cancelled выставляется при отмене до первого
  файла, после готового файла, одновременно с ошибкой текущего файла и перед
  запуском следующего. Общий статус — `Cancelled`, даже если текущий файл
  завершился `Failed`.
- **Конфликты имён**: `plan_batch` заранее группирует выходные имена
  (stem + относительный каталог) без учёта регистра. `chapter.txt` +
  `chapter.md` → `chapter.<ext>`; все участники конфликта получают `Skipped`
  с причиной, синтез не запускается, существующие файлы не перезаписываются.
  Конфликты входят в `BatchReport.conflicts` и в предупреждения плана.
- **Статусы и UI**: `BatchStatus`/`JobStatus` дополнены `Partial` и `NoWork`.
  Пакет с ошибками и успехами показывает «Частично / ЧАСТИЧНЫЙ УСПЕХ»;
  пустой пакет и пакет, где всё пропущено, — «Нет работы / НЕЧЕГО ДЕЛАТЬ»
  (синтез не выполнялся). K/N в UI обновляется на каждом `FileDone`, включая
  `Failed` и `Skipped`; прогресс чанков сбрасывается на данных отчёта файла.
- **Тесты**: 17 новых мок-тестов без ONNX (4 сценария отмены, 3 конфликта,
  пустой/все-пропущены, физические проверки junction/symlink, UI-состояния).
  Итог: 133 passed / 5 ignored; clippy 0. Реальный CPU-пакет: 3/1/1,
  статус «Частично», 9.3 с; одиночный G2 и WAV-паритет CLI — 374444 байта
  побитово (без изменений).

## Реализовано

- **Выбор источника**: один текстовый файл или каталог (`GuiSettings.batch`).
- **Снимок до генерации**: `batch::plan_batch` строит `Vec<BatchFile>` один
  раз; во время прогона список не перечитывается. Порядок стабилен:
  относительный путь без учёта регистра, затем точный.
- **Обход**: собственный DFS на `std::fs::read_dir` (без новых зависимостей),
  расширения `.txt/.md/.log` без учёта регистра. Символические ссылки
  пропускаются с предупреждением (не раскрываются); нечитаемые каталоги —
  предупреждение и продолжение.
- **Выходная папка**: если лежит внутри источника, её поддерево строго
  исключается из обхода. `out == source` — ошибка; `out` — предок источника
  не исключает файлы (проверяется отдельным тестом).
- **Структура результата**: `out_root/<относительный каталог>/<stem>.<ext>`.
- **Безопасные пути**: `output_path_for` отвергает абсолютные пути, `..` и
  любой выход за пределы `out_root` (лексическая нормализация + проверка).
- **Без перезаписи**: существующий результат → `Skipped` с причиной, синтез
  не запускается; гонка дополнительно закрыта `create_new`/`ffmpeg -n` в sink.
- **Изоляция ошибок**: сбой одного файла → `Failed`, остальные продолжаются.
  Общий статус: `Completed` при хотя бы одном успехе, `Failed` если успехов
  нет, `Cancelled` при «Стоп».
- **Отмена**: останавливает текущий синтез (`Cancelled`), следующий файл не
  запускается; оставшиеся помечаются `Skipped` («отменено до запуска»).
  `.partial` и диагностические журналы сохраняются (execute_job), ничего не
  удаляется автоматически.
- **Прогресс**: `FileProgress { index, total, done, chunks_total }` — в UI
  отдельно полоса `файл K/N` и полоса чанков текущего файла.
- **Отчёт**: `BatchReport` — по каждому файлу статус, причина, итоговый/
  черновик/диагностический/чанк-лог пути; агрегаты
  `Completed / Failed / Skipped / total` и признак отмены. Те же строки идут
  в журнал GUI.
- **Одиночный режим G2** не менялся: тот же `execute_job`; WAV-паритет CLI
  подтверждён (374444 байта побитово).

## Тесты

- 12 мок-тестов без ONNX: вложенные каталоги, одинаковые имена в разных
  подпапках, выход внутри источника, выход == источник, выход-предок,
  `..`-побег, существующий результат, изоляция ошибки, отмена, повторный
  запуск, одиночный файл, symlink (Windows, при наличии прав).
- UI-мок: события `FileProgress`/`FileDone` обновляют K/N и журнал.

  9.5 с; структура подкаталогов сохранена, существующий файл не перезаписан.
- `cargo test`: 116 passed / 5 ignored; `cargo clippy --all-targets`: 0.

## Переиспользование пула воркеров между файлами — НЕ реализовано

Сейчас каждый файл идёт через `execute_job → synthesize_stream → run_job`:
пул из N воркеров создаётся и освобождается на файл (существующий жизненный
цикл). Фиктивного переключателя «перезапуск каждые N файлов» нет.

Что потребуется для настоящего переиспользования:

1. Новый долгоживущий API в `app-core`: `PoolHandle` с `run(...)` на несколько
   файлов; `synthesize_stream` должен принимать готовый пул, а не создавать
   его внутри.
2. Сброс состояния на файл: seed/base_seed, EOS/anti-repeat, счётчики;
   задачи уже несут char_rules и паузы, но stateful-графы Pocket нужно
   привести к исходному состоянию.
3. Отмена: воркер, прерванный посреди чанка, имеет неопределённое состояние —
   его нужно пересоздать (или перезагрузить); нельзя переиспользовать «как
   есть» после отмены.
4. Ошибки/паника: `catch_unwind` уже есть в `run_job`, но при долгоживущем
   пуле упавший воркер надо исключить и пересоздать для следующего файла.
5. Владение/остановка: GUI `Drop`, «Стоп» и закрытие окна должны
   останавливать пул без осиротевших потоков; сейчас `JobHandle::drop`
   полагается на завершение одного задания.
6. Память/VRAM: Rust освобождает модели при drop, но при переиспользовании
   CUDA-пул удерживает ~1.4 ГиБ VRAM и арены ORT; нужна оценка фрагментации и
   пиков по N файлам.

Риски: нарушение побитового паритета/детерминизма seed, некорректная отмена,
изоляция паник, изменения публичного API app-core, удержание VRAM, гонки.
Решение: внедрять только после замеров выигрыша по времени старта/памяти и
отдельного разрешения; текущий per-file пул проще и безопаснее.
