# G6.2.1 — Hardening жизненного цикла гибридного пула 2×2

Дата: 2026-11-10. База: HEAD `40c363c` (G6.2). Верифицированный бэкап ДО
изменений: `<NAS>\Temp2\ShtormTTS-Windows-full-40c363c-
20261110-212916.zip`, SHA256
`7B591D5CAFEA0F38863A7180A7742FC0B10C571D0436593C5947EAB8C8C679C0`,
165/165 blob совпадают с HEAD.

Этап корректирующий: архитектура гибрида, математика Pocket/ONNX, EOS, seed,
чанкер, DSP, I/O Binding и механизм постоянного пула G6.1 не менялись.
Изменены только управление процессами, IPC-завершение и диагностика
жизненного цикла.

## 0. Итог

Устранены четыре класса ошибок управления дочерними процессами:

1. **Deadlock фатальной ошибки инициализации** — `reader.join()` больше не
   ждёт вечно: ожидающее overlapped-чтение снимается `CancelIoEx`, буферы и
   `OVERLAPPED` освобождаются только после возврата потока.
2. **Диспетчер не распознавал отсутствие работоспособных воркеров** —
   введены явные состояния процессов, startup timeout и проверка
   жизнеспособности по воркерам, а не по существованию PID.
3. **Потеря/переупорядочивание завершающих IPC-событий** — `Exiting`
   отправляется через единственный writer строго после `FileFinished` и
   `Stopped`; перед выходом очередь событий сливается с ограничением времени.
4. **Job Object не был гарантирован** — fail-closed: без действующего
   `KILL_ON_JOB_CLOSE` режим 2×2 не стартует; отказ назначения процесса
   завершает уже созданные собственные процессы и не начинает синтез.

## 1. Причины найденных зависаний

### 1.1. Фатальная ошибка `build_worker_env()`

Прежний код (`worker_main_impl`, G6.2):

```rust
let _ = ev_tx.send(Ev::WorkerError { worker: usize::MAX, .. });
let _ = ev_tx.send(Ev::Exiting);
drop(ev_tx);
let _ = writer.join();
let _ = reader.join();
return Ok(1);
```

`reader` — поток, заблокированный в `ReadFile` на Named Pipe. Диспетчер не
обязан закрывать канал (он ждёт событий), поэтому `reader.join()` мог не
вернуться никогда. Процесс оставался живым с мёртвыми воркерами; при
отсутствии назначенных файлов watchdog не срабатывал, а очередь могла
остаться с Pending-файлами.

### 1.2. «PID существует» ≠ «воркер может работать»

`Failure` одного воркера (`WorkerError { worker }`) и фатальная ошибка
процесса (`WorkerError { worker: usize::MAX }`) не переводили процесс в
терминальное состояние в модели диспетчера. Проверка
`child_alive.iter().all(|a| !a)` реагировала только на закрытие IPC/PID.
Процесс с двумя мёртвыми воркерами, но живым PID, не давал ни Ready, ни
новых событий — диспетчер ждал бесконечно (при отсутствии busy-файлов
watchdog тоже молчал).

### 1.3. Две параллельные записи в один канал

В штатной ветке `Exiting` отправлялся напрямую `send_ev(&end, ...)`
одновременно с writer-потоком, который ещё дописывал `FileFinished`/
`Stopped`. Даже при сериализации внутри `PipeEnd` порядок не гарантирован:
`Exiting` мог опередить события, а `std::process::exit(0)` обрывал запись.
При разорванном IPC прямой `send_ev` мог блокироваться в ожидании
overlapped-записи.

### 1.4. Необязательный Job Object

`ChildJobGuard::new()` при ошибке создания job сохранял `handle = None`, а
`assign_to_job(None, pid)` возвращал `Ok(())`. Пакет продолжался без
`KILL_ON_JOB_CLOSE`: обещанная защита от осиротевших CUDA-процессов не
гарантировалась. Отказ `AssignProcessToJobObject` только логировался.

## 2. Диаграмма жизненного цикла

### 2.1. Дочерний процесс

```
connect(pipe) ──► Started
     │
     ├── Init(test.fail_init) ──► WorkerError(usize::MAX) ──► Exiting ──►
     │                              finish_child(code=1) ──► EOF ──► exit(1)
     │
     ├── Init(init_delay_ms) ──► sleep ──► (внешний kill) ──► EOF ──► exit≠0
     │
     └── Init ──► build_worker_env
                     │
                     ├─ Err ──► WorkerError(MAX) ──► Exiting ──►
                     │           finish_child(code=1) ──► exit(1)
                     │
                     └─ Ok ──► worker_loop(wid):
                                 load Pocket ──► Ready ──►
                                 Assign ──► FileStarted ──►
                                 Generating ──► Finalizing ──► Publishing ──►
                                 FileFinished ──► Idle ──► ...
                                 (ошибка движка: FileFinished(Failed) ──►
                                  WorkerError(wid) ──► выход воркера)
                                 Shutdown ──► Stopped
                     │
                     └─ все воркеры join ──► Exiting (через ev_tx) ──►
                        writer flush (≤5 с) ──► CancelIoEx reader ──►
                        exit(0)
```

### 2.2. Диспетчер и состояние процесса

```
Starting ──Started──► Initializing ──все Ready──► Ready
   │                      │                       │
   │                      ├──WorkerError(wid)──► (если все воркеры мертвы)
   │                      │                       ▼
   │                      │                     Failed
   │                      ├──startup timeout──► Failed (kill своего PID)
   │                      │
   ├──WorkerError(MAX)──► Failed
   ├──PID/канал закрыт──► Exited
   └──Shutdown/Exiting/Stopped──► Stopping
```

Правила:

- **Ready** — все живые воркеры процесса готовы; **Busy** — хотя бы один
  занят файлом; **Initializing** — есть живой ещё не готовый воркер.
- **Failed** — фатальный `WorkerError(usize::MAX)` или погибли все воркеры.
- **Exited** — процесс завершился (PID/канал), даже если файлов у него не
  было.
- «Живой PID» без способного инициализироваться воркера не является
  основанием ждать.

## 3. Правила завершения Named Pipes

1. **Все операции — overlapped** (`FILE_FLAG_OVERLAPPED`, событие на
   операцию, `GetOverlappedResult`). Синхронный duplex-протокол взаимно
   блокируется.
2. `CancelIoEx(handle, NULL)` снимает ожидающие чтение/запись. Отменённая
   операция завершается `ERROR_OPERATION_ABORTED`; на границе кадра это
   трактуется как EOF.
3. Буферы и `OVERLAPPED` принадлежат ожидающему потоку и **не
   освобождаются**, пока он не вернулся из операции. Поэтому порядок:
   отмена → ограниченный `join` потока → закрытие HANDLE.
4. `DisconnectNamedPipe` (серверный конец) используется для принудительного
   разрыва: клиент получает EOF/`ERROR_BROKEN_PIPE`. Применяется только к
   собственному тестовому/дочернему соединению.
5. Если поток не завершился за `CHILD_IO_JOIN_TIMEOUT` (2 с) после отмены,
   дочерний процесс выходит принудительно: ОС освободит handle и память, но
   ожидание не станет бесконечным.
6. HANDLE закрывается ровно один владелец (`PipeEnd::Drop`); `PipeServer`
   передаёт владение в `accept` через `mem::forget`.

## 4. Порядок доставки завершающих IPC-событий

Штатное завершение:

```
worker_loop: FileFinished → (Idle)* → Stopped
main:        join всех воркеров → ev_tx.send(Exiting) → drop(ev_tx)
writer:      дописывает FIFO-очередь (включая Exiting) → выходит
reader:      CancelIoEx → EOF → поток выходит
process:     exit(0)
```

Гарантии:

- `Exiting` — **последнее** сообщение процесса; оно ставится в ту же очередь
  `mpsc`, что и события воркеров, после `join` всех воркеров.
- Прямая параллельная запись `send_ev(&end, Exiting)` удалена.
- Все клоны `ev_tx` у воркеров дропнуты до отправки `Exiting`, поэтому
  writer не может обогнать `FileFinished`/`Stopped`.
- Writer ограничен `CHILD_WRITER_FLUSH_TIMEOUT` (5 с); при разорванном канале
  он выходит по ошибке записи, затем `CancelIoEx` снимает чтение.
- Родитель видит `Exiting`, затем `Closed(EOF)`; код завершения — 0.
- При фатальной ошибке инициализации порядок тот же:
  `WorkerError(MAX) → Exiting → EOF`, код 1.

## 5. Поведение при отсутствии Ready-воркеров

`Dispatch::fail_if_no_capacity()` вызывается после каждого события и в
таймаут-ветке:

```
if all_done или cancelled           -> не трогать
if есть живой ready-воркер          -> ждать/работать
if есть процесс, способный init     -> ждать (не преждевременно)
иначе                               -> Failed всем оставшимся, выход
```

«Способен init» = процесс не в `Failed/Exited/Stopping` и у него есть живой
воркер с `ready=false`. Поэтому:

- процесс с одним busy-воркером и вторым ещё загружающимся **не** считается
  устоявшимся;
- молчащий процесс без единого Ready убивается по startup timeout, его файлы
  получают Failed;
- при гибели всех процессов незавершённые файлы получают явный Failed, а не
  теряются.

## 6. Startup timeout и watchdog

| Механизм | Значение | Действие |
|---|---:|---|
| `CHILD_CONNECT_TIMEOUT` | 60 с | процесс не подключился к каналу — запуск отменяется, свой PID убивается |
| `CHILD_STARTUP_TIMEOUT` | 120 с | у процесса нет готовых воркеров — kill своего PID, файлы Failed |
| `CHILD_WATCHDOG` | 300 с | у процесса есть назначенный файл, но нет событий — kill своего PID, файлы Failed |
| `CHILD_EXIT_TIMEOUT` | 15 с на процесс | после Shutdown процесс не вышел — принудительный kill |
| `CHILD_WRITER_FLUSH_TIMEOUT` | 5 с | недописанная очередь событий — CancelIoEx |
| `CHILD_IO_JOIN_TIMEOUT` | 2 с | поток не вернулся после отмены — принудительный exit процесса |

Дополнительно диспетчер раз в 100 мс проверяет `try_wait()` **даже без
назначенных файлов** (авария во время загрузки модели); событиям канала
даётся 1 с, чтобы дойти до диспетчера. Гибель PID обнаруживается и без
busy-файлов.

## 7. Политика Windows Job Object

- Job создаётся до первого процесса, `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`.
- **Fail-closed**: `ChildJobGuard::ready()` проверяется в
  `execute_batch_hybrid` до запуска. Ошибка → 2×2 не стартует, файлы
  кандидаты получают Failed с текстом «Windows Job Object … недоступна;
  выберите экономичный режим 1×2». GUI остаётся работоспособным.
- `assign(pid)` без действующего job возвращает ошибку. Спавнер убивает
  только что созданный собственный процесс и возвращает Err.
- Любой отказ запуска/назначения в `run_hybrid` — общий откат: уже
  созданные собственные процессы `kill()+wait()`, синтез не начинается.
- Job живёт всё время работы дочерних процессов (guard в
  `execute_batch_hybrid`); закрывается после штатного завершения. При
  аварийной гибели диспетчера ОС закрывает handle job — все дочерние PID
  завершаются (`E2E-I`).
- CPU, одиночный синтез и экономичный 1×2 не используют этот путь и не
  затронуты.

## 8. Ошибки загрузки ORT/Pocket

- `build_worker_env()` (модель/ORT/char_rules) — фатально для процесса:
  `WorkerError(MAX) → Exiting → EOF`, код 1, ограниченное завершение IPC.
- Загрузка Pocket в конкретном воркере (`real_worker_factory`) — фатально
  только для воркера: `WorkerError(wid)`, воркер больше не получает файлы;
  остальные воркеры процесса продолжают.
- Все воркеры процесса умерли — процесс переходит в `Failed`, его
  незавершённые файлы Failed; живой PID не считается работоспособным.
- Автоматического перезапуска процессов/Pocket после ошибки нет (политика
  G6.1/G6.2: состояние публикации может быть неопределённым).

## 11. Ограничения и оставшиеся риски

- Startup timeout (120 с) и watchdog (300 с) — эвристики: на экстремально
  медленном диске/машине легитимная загрузка может быть принята за
  зависание. Таймауты конфигурируются в `HybridDriver` (тесты используют
  короткие значения).
- `CancelIoEx` + `DisconnectNamedPipe` не дают гарантии «нулевого окна» при
  конкурентной записи: поток writer'а может получить ошибку записи, но не
  обращается к уже освобождённым буферам (буферы живут в потоке до join).
- Job Object fail-closed означает: при отказе ОС 2×2 недоступен, даже если
  процессы могли бы работать. Экономичный 1×2 остаётся.
- Проверка идентичности клиента канала — по PID; подмена PID в пределах
  сессии/пользователя не рассматривается как угроза (канал локальный,
  `PIPE_REJECT_REMOTE_CLIENTS`).
- Реальная визуальная приёмка живого GUI 2×2 и portable-комплект G6.2.1 —
  по результатам §11 итогового отчёта (если применимо).
