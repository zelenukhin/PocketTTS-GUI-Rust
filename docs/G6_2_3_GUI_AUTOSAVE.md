# G6.2.3 — автосохранение настроек и запуск GUI без консоли

Этап: пользовательские изменения интерфейса поверх G6.2.2a. Алгоритм синтеза,
IPC-протокол, Job Object и CUDA-пулы 1×2/2×2 **не менялись**.

Исходное состояние: HEAD `5e53b37` (G6.2.2a), бэкап на NAS
`ShtormTTS-Windows-full-5e53b37-20261111-005803.zip`, SHA256
`6E6A374B5FAE88055CB1F7060A498CEDCB531E872C16C11C4AB7191E4812EE10`,
166/166 blob совпадают с HEAD.

## 1. Как теперь сохраняются настройки

При **штатном закрытии окна** (крестик, Alt+F4, `CloseMainWindow`/WM_CLOSE)
текущие значения `GuiSettings` автоматически записываются в
`shtorm_gui_settings.json` рядом с exe — тот же путь и тот же сериализатор,
что у кнопки «Сохранить настройки». Сохраняются **все** поля структуры,
включая модель Fast/Slow/Custom, устройство и device ID, потоки/воркеры,
`batch_cuda_mode` (Economy 1×2 / MaxSpeed 2×2), режим одиночный/пакетный,
пути источника/голоса/вывода, форматы и пресеты MP3/Opus, температуру,
decode_steps, seed, EOS и anti-repeat, brightness, denoise, параметры пауз,
max_tokens, overwrite_existing, тему, состояния свёрток и неизвестные ключи
`extra` (round-trip без потерь). Кнопка «Сохранить настройки» оставлена как
немедленное ручное сохранение.

При следующем запуске пользователь видит параметры такими, какими оставил их
перед закрытием. Нажимать «Сохранить настройки» больше не требуется.

Политика «без изменений — не пишем»: при старте снимается сериализованный
снимок настроек; если сессия ничего не изменила, при закрытии файл не
перезаписывается вовсе (нет лишних временных файлов, содержимое остаётся
байт-в-байт).

Внутренний worker-режим `--internal-batch-worker` настройки **не читает и не
пишет** (вся конфигурация приходит по IPC). Диагностические `--portable-*`
режимы применяют `--device/--format` к копии в памяти и завершают процесс —
автосохранение в них структурно невозможно (выход до `eframe::run_native`).

## 2. При каком событии происходит сохранение

eframe 0.31.1: `update()` получает `viewport().close_requested()` на кадре
после `WM_CLOSE`; если в этом кадре отправлен `ViewportCommand::CancelClose`,
окно остаётся живым. Собственный `ViewportCommand::Close` индуцирует
`close_requested()` на следующем кадре — без явной защиты это даёт цикл
`Close → CancelClose → Save → Close → …`.

Введена явная машина состояний (`app.rs`, `enum CloseFlow`):

| Состояние | Смысл | Реакция на close_requested |
|---|---|---|
| `Idle` | обычная работа | нет задания → `Saving`; есть задание → отмена, `WaitingForJob`; **CancelClose** |
| `WaitingForJob` | ждём завершения фонового потока (семантика G2/G5.1: отмена между чанками, публикация дорабатывает, `.partial` и журналы остаются) | **CancelClose** (повторный крестик не обгоняет закрытие) |
| `Saving` | попытка автосохранения в кадре перехода | **CancelClose** |
| `SaveFailed` | ошибка записи, окно удерживается, показан диалог | **CancelClose** (нужен явный выбор) |
| `Closing` | решение принято, `ViewportCommand::Close` отправлен ровно один раз | **не отменяем** — процесс завершается |

Переходы: `Idle → WaitingForJob` (крестик при живом задании, `cancel` ставится
атомарно, UI-поток не ждёт CUDA/IPC) → `Saving` (поток завершён) →
`Closing`/`SaveFailed`. `Closing` всегда мононитонен: повторной инициализации
закрытия нет, бесконечный цикл исключён (юнит-тест
`close_after_closing_command_never_cancels_again`).

Дополнительная страховка — `eframe::App::on_exit(&mut self, _gl)` (сигнатура
eframe 0.31 с default-фичей glow): если выход произошёл МИМО штатного потока
(состояние осталось `Idle`), делается лучшая попытка сохранения по тем же
правилам. `Drop` для этого не используется.

## 3. Обработка ошибки записи

Используется прежний `settings::save_settings`: уникальный tmp через
`create_new` → `MoveFileExW REPLACE_EXISTING|WRITE_THROUGH`. Существующий JSON
не разрушается ни при ошибке сериализации, ни при отказе замены.

- **Ошибка записи** (каталог недоступен, диск полон, файл занят/read-only):
  окно не закрывается, показывается диалог «Настройки не сохранены» с
  текстом ошибки и выбором «Повторить сохранение» / «Выйти без сохранения».
  Ложного сообщения об успехе нет; старый JSON остаётся целым. Повтор
  выполняет ту же атомарную запись; повторный крестик не закрывает окно
  молча.
- **Повреждённый/нечитаемый существующий JSON** (ошибка разбора, BOM от
  внешнего редактора, нет прав на чтение): при старте фиксируется состояние
  `Unreadable`, статус сообщает «настройки не загружены …; конфиг не будет
  перезаписан автоматически». При закрытии автосохранение **пропускается** —
  непрочитанный пользовательский файл остаётся байт-в-байт; причина
  записывается в журнал. Ручная кнопка сохранения остаётся осознанным
  решением пользователя.
- **Первый запуск** (файла нет): это не «повреждённый конфиг» — автосохранение
  разрешено и создаёт файл при наличии изменений.
- Обычная работа без правок — файл не трогается (см. §1).

## 4. Почему выбран такой способ отключения консоли

**Решение: один exe, Windows GUI-подсистема для release.**

```rust
#![cfg_attr(all(target_os = "windows", not(debug_assertions)), windows_subsystem = "windows")]
```

- PE-заголовок release-бинаря: `Subsystem = 2 (WINDOWS_GUI)`; debug-сборка
  остаётся консольной (3) — логи разработки видны в терминале.
- GUI-подсистема не выделяет процессу консоль: ни при двойном клике, ни при
  запуске из PowerShell. Дочерние worker-процессы — тот же exe; они тоже
  GUI-подсистемы и окон не открывают. Дополнительно их спавн явно помечен
  `CREATE_NO_WINDOW` (закрепляет поведение при любом способе запуска).
- Диагностика сохранена в том же exe. Stdout/stderr пишутся через штатные
  Rust-потоки: при явном перенаправлении (System.Diagnostics.Process с
  `RedirectStandardOutput/Error`, PowerShell-конвейер, `> file 2>&1`, pipes)
  вывод и ExitCode доступны полностью. Проверено на реальном release-exe:
  `--help` (код 0), `--portable-check` (код 0), ошибочные аргументы (код 2,
  stderr), `--portable-selftest-hybrid` (2 процесса/4 воркера/6 файлов, код 0).
- Если потоки отсутствуют вовсе (двойной клик, «Выполнить»), критичная ошибка
  разбора аргументов показывается нативным `MessageBoxW` — иначе она была бы
  невидимой. При работающем stderr MessageBox не появляется и автоматизацию
  не блокирует.
- Консольные дочерние процессы (`ffmpeg`, `nvidia-smi`) из GUI-подсистемы
  получали бы **собственное** консольное окно на каждый запуск (запуск
  энкодера, диагностика VRAM). Поэтому все продакшн-спавны помечены
  `CREATE_NO_WINDOW` через общий `app_core::hide_console()`; stdio у них уже
  явно перенаправлены (piped/null/output), поведение и ExitCode не менялись.

Отклонённые варианты: `ShowWindow(GetConsoleWindow(), SW_HIDE)` — может скрыть
консоль пользователя; `FreeConsole()` — окно успевает мигнуть, а диагностика
теряет вывод; отдельный `shtorm-cli.exe` — второй бинарь не нужен, GUI-подсистема
проходит все реальные проверки (двухбинальный вариант оставлен резервом).

## 5. Как сохранена headless-диагностика

- Все прежние флаги работают из того же exe: `--help`, `--portable-check`,
  `--portable-selftest`, `--portable-selftest-batch`,
  `--portable-selftest-cancel`, `--portable-selftest-hybrid`,
  `--internal-batch-worker <pipe>`.
- Строгая CLI-диспетчеризация G6.1.1/G6.1.2 сохранена: неизвестный/повторный
  флаг — exit 2 до открытия окна и загрузки Pocket; `--help` — exit 0.
- `--internal-batch-worker` запускается только диспетчером, окно не открывает
  никогда, настройки не читает/не пишет.
- Scripts: `tools/g611_cli_smoke.ps1` и `tools/g62_hybrid_smoke.ps1` проходят
  без изменений (ALL PASS) — они используют явные redirects, стандартный для
  проекта способ получения диагностики.

## 8. Известные ограничения

- Сохранение выполняется только при **штатном** закрытии окна. Завершение
  через Диспетчер задач, `taskkill /F`, выключение/завершение сеанса Windows
  или аварийное падение процесса настройки не сохраняет — это осознанно
  (никакого `std::process::exit` на обычном close нет, прерывать публикацию
  нельзя).
- Если конфиг нечитаем (в т.ч. JSON с BOM от внешнего редактора), он больше
  не перезаписывается автоматически: автосохранение молча пропускается,
  исправить файл можно вручную или кнопкой «Сохранить настройки».
- Ошибка автосохранения требует решения пользователя — окно остаётся
  открытым (это не зависание: процесс жив, виден диалог).
- При запуске диагностики из интерактивного `cmd.exe` (без redirect) cmd не
  ждёт GUI-приложение, поэтому вывод может появиться асинхронно или не
  дождаться скриптом; для сценариев использовать redirect/PowerShell
  (`& exe --portable-check`) — задокументировано в README комплекта.
  MessageBox для ошибок аргументов появляется только когда stderr
  отсутствует вовсе.
- Portable-комплект проверен на машине разработки; чистая Windows-VM
  по-прежнему не проверялась.
