создан ДО изменений:
`<NAS>\Temp2\ShtormTTS-Windows-full-fdcc485-20261110-172531.zip`,

## 0. Итог

Пакетный CUDA-режим GUI получил осознанный выбор:

- **Экономичный — 1 процесс × 2 воркера** (проверенный G6.1 пул, ~4.9 ГБ VRAM);
- **Максимальная скорость — 2 процесса × 2 воркера** (гибрид H22 из
  CUDA-P2B.3: два НЕЗАВИСИМЫХ дочерних процесса синтеза, в каждом два
  постоянных `Pocket`; ~9.2 ГБ VRAM).

GUI остаётся диспетчером и владельцем общей очереди; ONNX грузится только
в дочерних процессах (в GUI-процессе CUDA-контекстов нет). Результаты
дочерних процессов неотличимы побитово: все WAV гибрида — байт-в-байт
равны экономичному 1×2 (а он — пофайловому пути, G6.1).

Проверено: 12/12 WAV побитовый паритет, отмена и повтор, overwrite,
MP3/Opus, принудительная гибель дочернего PID (файлы получают явный
Failed, выживший процесс доделывает очередь), smoke реального EXE и
headless fake-режим без CUDA/моделей. Числа производительности — §11.

## 1. Архитектура

```
GUI-процесс (PocketTTS-GUI-Rust.exe) — ДИСПЕТЧЕР
  ├─ preflight пакета (конфликты/существующие/безопасность путей) ДО процессов
  ├─ VRAM-префлайт (4 Pocket × 2355 МБ + 1500 МБ запаса)
  ├─ общая очередь файлов (владеет только диспетчер)
  ├─ Named Pipe #0  ⇄  дочерний процесс 0 (PocketTTS-GUI-Rust.exe --internal-batch-worker)
  │                       ├─ Pocket #0 (5 ONNX-сессий) — воркер 0
  │                       └─ Pocket #1 — воркер 1
  └─ Named Pipe #1  ⇄  дочерний процесс 1
                          ├─ Pocket #2 — воркер 0
                          └─ Pocket #3 — воркер 1
```

- Всего процессов Windows: 3 (GUI + 2 worker-процесса); процессов
  CUDA-инференса — **два**, как в экспериментальной топологии H22 P2B.3.
- Дочерние процессы — ТОТ ЖЕ бинарник во внутреннем режиме
  `--internal-batch-worker <имя_канала>`: окно никогда не открывается,
  exe-относительный резолвер портативной сборки работает идентично,
  `tools/build-portable.ps1` не меняется (отдельного EXE нет).
- Дочерние процессы приписываются к Windows Job Object с
  `KILL_ON_JOB_CLOSE`: аварийная гибель GUI не оставляет осиротевших
  CUDA-воркеров.

### Выбор `--internal-batch-worker`

Строгий парсер CLI (G6.1.1/G6.1.2) дополнен внутренней командой: имя канала
обязательно, значение-флаг отклоняется, сочетание с диагностическими
командами/опциями — ошибка; любая опечатка имени флага — «неизвестный
аргумент», exit 2, окно НЕ открывается. Значение приходит от диспетчера
(уникальное имя `\\.\pipe\shtorm_tts_<tag>_<pid>_<наносекунды>`).

## 2. IPC (Named Pipes)

`crates/gui/src/ipc.rs`:

- **Duplex Named Pipe**, byte mode, `PIPE_REJECT_REMOTE_CLIENTS`, DACL по
  умолчанию (текущий пользователь): локальное соединение, НЕ сетевой сервер.
- Кадр: `u32 LE` длина + JSON; лимит кадра 64 МиБ; EOF на границе кадра =
  сторона завершилась.
- **Все операции OVERLAPPED** (`FILE_FLAG_OVERLAPPED`, событие на каждую
  операцию, `GetOverlappedResult`). Причина: на синхронном handle блокирующий
  `ReadFile` приостанавливает `WriteFile` на ТОМ ЖЕ handle — duplex-протокол
  «постоянное чтение событий + команды диспетчера» на синхронных handle
  взаимно блокируется (обнаружено E2E-тестом; регрессия
  `ipc::tests::duplex_concurrent_read_write`).
- `ConnectNamedPipe` — overlapped с таймаутом 60 с: умерший до подключения
  ребёнок не блокирует диспетчер.
- **Идентичность дочернего процесса** проверяется
  `GetNamedPipeClientProcessId` == PID запущенного `Child`; подключение
  постороннего процесса — диагностика + отказ.
- stdout/stderr в протоколе не участвуют (управление — только канал).
- Приём/передача: диспетчер — выделенный поток чтения на процесс; ребёнок —
  поток чтения команд + поток записи событий (строго последовательная запись).

### Протокол

Команды диспетчера (`cmd`):
`init { settings, workers, fake }`, `assign { worker, pos, input, relative,
out, seed }`, `cancel`, `shutdown`.

События процесса (`ev`): `started { pid }`, `pocket_loaded { worker, load_ms }`,
`ready { worker }`, `file_started`, `file_progress { done, total }`,
`file_phase { generating|finalizing|publishing }`, `file_finished { report }`,
`idle { worker }`, `worker_error { worker (usize::MAX — фатальная ошибка
процесса), error }`, `stopped { worker }`, `exiting`.

Все события несут процесс (по каналу), воркер и позицию файла; `FileReport`
сериализуется целиком (serde) — отчёт не пересобирается по частям.

## 3. Жизненный цикл процессов

1. Диспетчер: preflight пакета и подготовка путей (G5/G6.1) ДО процессов.
2. На каждый процесс — канал создаётся ДО `Command::spawn`; процесс
   приписывается к Job Object; принимается соединение с проверкой PID.
3. Ребёнок: `init` → резолв модели + `char_rules` + инициализация ORT В
   ПРОЦЕССЕ → потоки воркеров загружают свои `Pocket` параллельно
   (`pocket_loaded` + `ready` на воркера).
4. Диспетчер назначает файлы освободившимся воркерам (общая очередь).
5. `shutdown` после терминальных результатов всех файлов: воркеры
   освобождают `Pocket` (в своих потоках), процесс шлёт `exiting` и
   завершается с кодом 0. Диспетчер ждёт выхода до 15 с, затем — kill
   ТОЛЬКО своих дочерних процессов.
6. Отчёт собирается в порядке плана; `pool_processes = 2`,
   `pool_workers = 4`, `pool_loads = 4` (ровно 4 загрузки Pocket на пакет).

Загрузка моделей: 4 Pocket = 20 ONNX-сессий на пакет; каждая модель
загружается один раз за пакет в своём процессе. Переход файл→файл — без
загрузок (постоянные Pocket, как G6.1).

## 4. State machine файла и общая очередь

- `Pending → Assigned → Generating → Finalizing/Publishing →
  Completed/Skipped/Failed/Cancelled`.
- Очередь принадлежит диспетчеру; **освободившийся воркер любого процесса
  берёт следующий файл** — статического закрепления половины пакета нет.
- Один файл целиком выполняет один `Pocket` (`synthesize_stream_with_worker_factory`,
  workers=1); чанки между процессами не делятся.
- Ровно один терминальный результат на файл: повторный `file_finished` того
  же файла игнорируется с диагностикой «повторное завершение не учтено»
  (двойной публикации нет). Незапущенные при отмене — Skipped «отменено до
  запуска»; назначенные без результата (гибель процессов) — Failed.
- Per-file seed разрешается ДИСПЕТЧЕРОМ (фиксированный из настроек или
  случайный на файл) и передаётся в `assign`; воркер ставит его на
  постоянный Pocket перед первым чанком (паритет свежей загрузке, G6.1).

## 5. Отказоустойчивость

- **Гибель дочернего процесса** (включая CUDA OOM): обнаруживается разрывом
  IPC + кодом выхода; все назначенные ему незавершённые файлы получают
  ЯВНЫЙ Failed с диагнозом («дочерний процесс погиб до завершения файла»),
  очередь доделывает выживший процесс. Автоматического повтора нет —
  состояние публикации может быть неопределённым (требование задания §9).
- **Ошибка движка в одном воркере**: файл получает Failed (отчёт приходит
  ДО `worker_error`), Pocket не переиспользуется, воркер останавливается;
  файлы идут остальным. Гонка «назначение между FileFinished и
  WorkerError» закрыта: воркер отвергает накопленные назначения явным
  Failed, диспетчер при `worker_error` закрывает свой `busy`-файл.
- **Фатальная ошибка процесса** (модель/ORT не поднялись, `worker=usize::MAX`):
  все его файлы Failed, его воркеры мертвы; выживший процесс продолжает.
- **Watchdog**: процесс с НАЗНАЧЕННЫМ файлом, молчащий дольше 300 с,
  принудительно завершается (только свой), файлы — Failed. Молчащий БЕЗ
  работы процесс легитимен (ждёт shutdown) и не трогается.
- **Ни одного живого процесса**: оставшиеся файлы Failed «воркеры дочерних
  процессов завершились» — задание не исчезает молча.
- **Запись в канал мёртвому процессу**: назначение не теряется — ребёнок
  отвечает терминальным Failed «воркер недоступен», если воркер уже мёртв.
- CUDA OOM не вызывает бесконечных перезапусков: дети не перезапускаются
  ни при каких ошибках.

## 6. Безопасность файлов (G5/G5.1/G6.1 сохранены)

- Preflight пакета ДО процессов: конфликты имён, существующие результаты,
  unsafe-пути; каталоги создаются до воркеров.
- **Каждый дочерний процесс повторно проверяет** `ensure_output_path_safe`
  непосредственно перед созданием sink (не полагается на preflight GUI).
- Уникальный `.partial`, `create_new`, атомарная публикация
  (`MoveFileW` без замены / `MoveFileExW REPLACE|WRITE_THROUGH` при
  overwrite_existing); `finish()`/`publish()` раздельны; отмена до точки
  решения не публикует; старый файл при ошибке/отмене не изменяется;
  `.partial` отменённых файлов сохраняется для диагностики.
- Ошибки публикации Pocket не отравляют (кодирование прошло успешно);
  ошибки движка/отмены — отравляют (как G6.1).

## 7. Отмена и закрытие GUI

Кнопка «Стоп» (и закрытие окна) → в потоке задания (UI не блокируется):

1. Диспетчер прекращает выдачу новых файлов.
2. Обоим живым процессам отправляется `cancel`; генерация прерывается
   между чанками; файлы в Finalizing/Publishing **дорабатывают публикацию**
   (единая точка решения G5.1).
3. Каждый файл получает терминальный результат (Completed/Cancelled/
   Skipped «отменено до запуска»).
4. `shutdown` → освобождение Pocket → выход процессов (с эскалацией kill
   только для собственных детей через 15 с).
5. GUI возвращается в готовность; повторный пакет штатный (готовое
   пропускается). Ранее опубликованные файлы целы.

## 8. VRAM: префлайт, откат, освобождение

- Порог гибрида: `4 × 2355 МБ + 1500 МБ = 10920 МБ` свободной VRAM.
  Обоснование: P2B.3 — пик 9.2–9.4 ГБ на 4 Pocket; B4 (4 контекста) словил
  CUDA OOM при ~11.5 ГБ свободных, т.е. 9.2 ГБ — не гарантированный максимум;
  запас 1.5 ГБ консервативнее 0.9 ГБ у 1×2.
- Недостаточно VRAM / nvidia-smi недоступен → **четыре Pocket НЕ
  загружаются**, режим откатывается на экономичный 1×2 с записью в журнал
  (объяснение и предложение освободить VRAM); выбор пользователя не
  игнорируется молча.
- Кандидатов меньше 4 → экономичный режим с пояснением (лишние Pocket не
  грузятся).
- Частичный сбой загрузки Pocket в детях: процессы штатно освобождают уже
  созданные Pocket и завершаются; файлы-кандидаты Failed с диагнозом;
  повторов нет, GPU в неизвестном состоянии не остаётся.
- После нормального завершения, Cancel и гибели процесса VRAM возвращается
  к базе (замеры — §9, §11).

## 11. Производительность (реальный GUI-путь)

Методика (`real_batch_cuda_hybrid_bench`): набор main12 (12 файлов, 77 чанков,
454.0 с аудио), каждый режим — прогрев + **3 измеренных повтора**, каждый
прогон в новом каталоге. **Cold wall** — полный `execute_batch` (включая
загрузку Pocket); **Warm wall** — от `BatchWorkersReady` (все воркеры готовы)
до последнего `FileDone` (без загрузок и preflight). Одновременно
сэмплировались nvidia-smi (util, VRAM ~0.3 с) и CPU. Побитовая сверка:
все 12 WAV КАЖДОГО прогона (9 × 12 = 108) равны эталону экономичного режима.

| Режим | Pocket / процессов | Cold, с (3 повтора) | Warm, с (3 повтора) | Warm реч-с/с | VRAM max | GPU util | CPU |
|---|---|---:|---:|---:|---:|---:|---:|
| Экономичный 1×2, t4 | 2 / 1 | 44.20 / 47.36 / 44.26 (45.27) | 42.56 / 45.74 / 42.62 (**43.64**) | 10.67 / 9.92 / 10.65 (10.41) | 4850–4969 МБ | 44–47% | 48–58% |
| **Максимум 2×2, t4** | **4 / 2** | **41.78 / 42.33 / 42.08 (42.06)** | **38.77 / 38.56 / 39.05 (38.79)** | **11.71 / 11.77 / 11.62 (11.70)** | **9289–9305 МБ** | **65–68%** | **67–69%** |
| Максимум 2×2, t2 | 4 / 2 | 42.68 / 42.48 / 42.31 (42.49) | 39.07 / 39.55 / 39.35 (39.32) | 11.62 / 11.48 / 11.54 (11.55) | 9283–9360 МБ | 67–69% | 68–72% |

- **2×2 t4 против 1×2: warm −11.1%** (43.64 → 38.79 с), cold −7.1% (45.27 →
  42.06 с); warm throughput **+12.4%** (10.41 → 11.70 реч-с/с). Диапазоны
  warm-повторов не пересекаются (42.56–45.74 против 38.56–39.05).
- **Оверхед GUI/IPC ≈ 0**: диагностический H22 P2B.3 — 38.88 с warm,
  GUI 2×2 — 38.79 с; A2 P2B.3 — 43.57, GUI 1×2 — 43.64. Разница ≤0.2% —
  в пределах шума стенда; диспетчеризация+IPC не съедают выигрыш.
- **threads=2 против threads=4 в GUI**: 39.32 против 38.79 с (+1.4%, НЕ
  −2.7% как в P2B.3). Разница ≤1.5% — сессионный дрейф; устойчивого
