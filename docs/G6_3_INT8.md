## 1. Резюме

Добавлен явный выбор точности графов: варианты «Shtorm-v2 Fast (INT8)» и
«Shtorm-v2 Slow (INT8)» в существующем списке «Модель» (отдельного поля
«точность» в GUI нет). INT8 — **динамически-квантованные** графы
`flow_lm_main_int8 / flow_lm_flow_int8 / mimi_decoder_int8` + два всегда-FP32
графа (`mimi_encoder`, `text_conditioner` — INT8-версий не существует).
Молчаливого отката между точностями нет: отсутствующий файл — явная ошибка.

Главные факты (замеры ниже):

- **CPU INT8 — быстрее и легче**: −32% (Fast) / −25% (Slow) времени на чанк,
  private bytes −55%/−52%.
- **CUDA INT8 — работает, но в ~2.7× медленнее FP32**: квантованные узлы
  CUDA EP не выполняет (профилирование это доказало), они идут на CPU EP с
  покадровыми копиями через PCIe. Режим оставлен доступным и помечен в GUI
  предупреждением; переключение/блокировки нет.
- **FP32 не изменился**: WAV-выход побитово совпадает с эталонным бинарем
  `af005f7` (CPU и CUDA, Fast и Slow).

## 2. Исследование графов (G6.3a)

Инструменты: `out/g63_graph_analysis.py` (protobuf-анализ, onnx 1.23.0),
пример `crates/shtorm-engine/examples/int8_meta.rs` (загрузка тем же билдером
сессий, что в `Pocket::load`), ORT-профилирование (`--profile-dir` в smoke).

### 2.1 Интерфейсы графов

Все три INT8-графа имеют интерфейсы, **идентичные FP32** (имена, типы,
размерности входов/выходов) — проверено и на protobuf-уровне, и по
метаданным созданных ORT-сессий:

| Граф | FP32: in/out | INT8: in/out | Идентичность |
|---|---|---|---|
| flow_lm_main (main) | 20 / 20 | 20 / 20 | да (both fast/slow) |
| flow_lm_flow | 4 / 1 | 4 / 1 | да |
| mimi_decoder | 57 / 57 | 57 / 57 | да |
| mimi_encoder | 38 in | — (INT8 нет) | — |
| text_conditioner | 2 in | — (INT8 нет) | — |

Числа для ru-v2-fast; ru-v2-slow — те же значения. Полные дампы:
`out/g63/graph_analysis.json`, `out/g63/int8_meta_{fast,slow}_cpu.txt`,
`out/g63/int8_meta_fast_cuda.txt`.

Следствие: KV-cache/состояния (`state_*` ↔ `out_state_*`), привязка входов
по именам и CUDA I/O Binding (`io_states.rs`) работают без изменений —
графы взаимозаменяемы на уровне сессии.

### 2.2 Тип квантования и операторы

Квантование **динамическое** (по выводу onnxruntime.quantization): узлы
`DynamicQuantizeLinear` (квантование активаций на лету) + `MatMulInteger`
(целочисленный MatMul с int8-весами и zero-point). Никаких статических
`QLinearConv/QGemm/QLinearMatMul` и `ConvInteger` в графах нет.

| Граф (fast) | узлов FP32 | узлов INT8 | DQL | MatMulInteger | int8-инициализаторы |
|---|---|---|---|---|---|
| flow_lm_main | 1508 | 1613 | 26 | 26 | 52 |
| flow_lm_flow | 335 | 458 | 20 | 26 | 52 |
| mimi_decoder | 820 | 852 | 8 | 8 | 16 |
| mimi_encoder | 716 | — | — | — | — |
| text_conditioner | 1 | — | — | — | — |

ru-v2-slow: те же количества (1496/1601, 335/458, 816/848). Размеры файлов:
main 302.4→75.9 МБ, flow 39.1→9.9 МБ, decoder 41.4→22.6 МБ.

### 2.3 Таблица совместимости (итог G6.3a)

| Граф | CPU EP: загрузка/выполнение | CUDA EP: загрузка | CUDA EP: фактическое выполнение |
|---|---|---|---|
| flow_lm_main_int8 | OK (379 мс) | OK (651 мс) | смешанное: квант-узлы на CPU (см. §3) |
| flow_lm_flow_int8 | OK (77 мс) | OK (296 мс) | смешанное |
| mimi_decoder_int8 | OK (161 мс) | OK (365 мс) | смешанное |
| mimi_encoder (FP32) | OK | OK | как раньше |
| text_conditioner (FP32) | OK | OK | как раньше |

Успешное создание CUDA-сессии НЕ означает размещения узлов на GPU (CPU EP —
fallback) — фактическое распределение измерено профилированием (§3).

## 3. CUDA: фактическое распределение по Execution Providers

Прогон Fast INT8 CUDA (smoke, `--profile-dir out/g63/prof_cuda_int8`,
2 чанка, I/O Binding активен — лог «io binding active; state[0] on Cuda»).
Разбор: `out/g63_analyze_profile.py`, сырые JSON — `out/g63/prof_cuda_int8/`.

| Сессия | событий узлов | CUDA EP | CPU EP | квант-узлы (все на CPU) | Memcpy |
|---|---|---|---|---|---|
| flow_lm_main_int8 | 94525 | 68495 (72.5%) | 26030 (27.5%) | 2470 DQL + 2470 MMI | 3610 ToHost + 7220 FromHost |
| flow_lm_flow_int8 | 31595 | 27501 (87.0%) | 4094 (13.0%) | 1780 DQL + 2314 MMI | 1602 ToHost + 4094 FromHost |
| mimi_decoder_int8 | 2940 | 2304 (78.4%) | 636 (21.6%) | 48 DQL + 48 MMI | 48 ToHost + 144 FromHost |
| mimi_encoder (FP32) | 362 | 247 | 115 | — | 4 FromHost |
| text_conditioner (FP32) | 2 | 2 | 0 | — | — |

Выводы:

1. **`MatMulInteger` и `DynamicQuantizeLinear` CUDA EP не поддерживает** —
   каждый такой узел выполняется на CPU EP. Это и есть «многократное
   копирование между CPU и GPU»: на 2 чанка main-графа — 3610 D2H и 7220 H2D
   Memcpy-событий.
2. Выполнение на CUDA **смешанное** (в main лишь 72.5% событий узлов на
   CUDA EP; по CPU-времени узлов доля CPU EP ещё значимее — 978 мс против
   1687 мс аннотированных CUDA за прогон).
3. **CUDA I/O Binding совместим с INT8** и активен (интерфейсы состояний
   идентичны FP32; инициализация и кадры без ошибок, выход конечен).
4. ru-v2-slow имеет идентичный набор квант-операторов (26/26/8), поэтому
   распределение EP то же; отдельно не профилировался.
5. `device=CUDA` в логах — не доказательство GPU-инференса; доказательство —
   этот профиль + VRAM-дельта.

## 4. Реализация (G6.3b)

### 4.1 Движок (`crates/shtorm-engine/src/pocket.rs`)

- Новый `pub enum ModelPrecision { Fp32 (default), Int8 }` +
  `GraphStems` (стемы пяти графов): единый механизм разрешения имён.
  Fp32 → прежние пять файлов; Int8 → `flow_lm_main_int8/flow_lm_flow_int8/
  mimi_decoder_int8` + `mimi_encoder/text_conditioner` (FP32).
- `LoadOptions.precision` (дефолт Fp32 — исходное поведение). Отсутствие
  выбранного файла — явная ошибка с именем и точностью («молчаливый откат
  … запрещён»).
- Математика семплирования, EOS, seed, чанкование, анти-повторы, DSP,
  клип-гарды — не менялись. CUDA-ограничения FP32/TF32 прежние.

### 4.2 app-core

- `PipelineOptions.precision` → `real_worker_factory` передаёт его в каждый
  `Pocket` (пул G6.1, постоянный пул, гибрид — один и тот же путь).
- CLI: `--precision fp32|int8` у `synthesize`, `smoke` (+`--profile-dir`),
  `bench`; диагностические бинари diag_p2b2/p2b3/ep_probe зафиксированы на
  Fp32.

### 4.3 GUI

- `ModelChoice::{FastInt8, SlowInt8}` — ОДИН список «Модель» из 5 пунктов:
  `Shtorm-v2 Fast (FP32)` (дефолт-семантика прежняя), `Shtorm-v2 Fast (INT8)`,
  `Shtorm-v2 Slow (FP32)`, `Shtorm-v2 Slow (INT8)`, `Свой каталог ONNX`.
  Отдельного поля точности нет; выбор пункта задаёт и модель, и точность.
- `ModelChoice::precision()/sub_dir()/label()`; сериализация: `"Fast"`,
  `"Slow"`, `"FastInt8"`, `"SlowInt8"`, `"Custom"` — старые конфиги
  загружаются как прежде (FP32), unknown-key round-trip сохранён.
- `resolve_model_dir` (gui/job.rs): Int8 проверяет ВСЕ ТРИ int8-файла
  (ошибка называет файл и запрещает fallback); Fp32 — прежняя проверка
  `flow_lm_main.onnx`.
- Подсказка при INT8: «3 квантованных графа … + 2 FP32 …»; предупреждение
  (оранжевый текст) при CUDA+INT8 — «работает, но ~2.7× медленнее FP32 …
  для INT8 рекомендован CPU. Выбор не меняется автоматически». Блокировки
  комбинации нет (задание выполняется как выбрано).
- IPC гибрида 2×2: `Cmd::Init` несёт полный `GuiSettings` — новые варианты
  доходят до дочерних процессов без изменений протокола (wire round-trip
  тестом `init_carries_int8_model_choice_over_ipc`).

### 4.4 Portable (`tools/build-portable.ps1`)

- В каждый каталог модели копируются три INT8-графа (проверка наличия и
  размер sanity-check 50–100 МБ для main_int8); прежний запрет INT8 убран.
- `-SkipInt8Models` — компактный FP32-only комплект.

### 6.2 Память

- CPU: INT8 снижает private bytes примерно вдвое (475→213, 499→240 МБ) —
  int8-веса main/flow/decoder в 1.8–4× меньше.
- CUDA (частные байты процесса): FP32 ~2.95–2.97 ГБ, INT8 ~2.54–2.70 ГБ.
  VRAM по nvidia-smi (cold-прогоны smoke): FP32 +1461 МБ, INT8 +1137 МБ.
  Существенной экономии VRAM нет — веса main относительно рабочих буферов
  CUDA-контекста не доминируют.
- Загрузка моделей: INT8 быстрее (main 379 мс против 790 мс CPU; 651 против
  962 мс CUDA).

### 6.3 Пакетные режимы

- CPU-пакеты идут пофайловым путём (как раньше); real-тест
  `real_batch_cpu_int8` — 2 файла, пул 2 воркера, 2/2 Completed,
  INT8-выход побайтово ≠ FP32 (доказательство реальной загрузки INT8).
- Гибрид 2×2 и пул 1×2 — CUDA-режимы; с INT8 каждый Pocket наследует
  замедление §6.1 (принципиальных препятствий нет: wire-передача выбора
  доказана, Pocket::load один и тот же). Бенчмарк гибрид+INT8 не проводился
  как заведомо проигрывающий: основание — §3 (покадровые PCIe-копии в
  каждом из 4 Pocket) и §6.1 (+167–175% на чанк). Решения «увеличить число
  CUDA-воркеров под INT8» нет — запаса скорости нет.
- Проверено переключение точности между заданиями: смена ModelChoice
  меняет только путь загрузки Pocket (сессии не переиспользуются между
  заданиями с разными настройками — как и прежде для fast/slow).

## 10. Ограничения

- CUDA INT8 — экспериментальный режим: корректен, но в 2.7× медленнее FP32
  (квант-узлы на CPU EP, покадровые PCIe-копии; §3). Не использовать для
  производственного синтеза; предупреждение в GUI.
- VRAM INT8 почти не экономит (−0.3 ГБ); экономия — на CPU (RAM вдвое,
  время −25…−32%).
- Качество INT8 не оценивалось человеческим прослушиванием в этом этапе —
  только автоматические метрики (§5) и WAV для прослушивания.
- Гибрид 2×2 с INT8 не бенчмаркировался (принципиально медленнее, §6.3).
- INT8-файлы в portable — hardlink на исходники Downloads (тот же том);
  перенос комплекта на другую машину требует замены моделей на копии.
