# G6.7 — Единый постоянный пул чанков для CPU/CUDA, одиночного файла и каталога

Дата: 2026-11-12. HEAD до этапа `57dfbc0` (G6.6; верифицированный NAS-бэкап
`ShtormTTS-Windows-full-57dfbc0-20261112-194312.zip`, SHA256
`9534FCF77D083E3B04622DE135382D41D5F31CDEEB8A7F251396CD145B41190B`,
174/174 blob совпадают).

Главный результат: вместо распределения ФАЙЛОВ между Pocket распределяются
ЧАНКИ текущего файла. Файлов в обработке всегда максимум один; чанки
текущего файла синтезируются параллельно всеми разрешёнными воркерами;
пул Pocket постоянный в рамках задания (модели загружаются один раз).
Действует для CPU и CUDA, для одиночного TXT и каталога.

## 1. Архитектура

```text
Настройки P/W/C/T
        |
Постоянный пул Pocket (создаётся один раз на задание)
        |
Текущий TXT -> build_file_tasks -> очередь чанков
        |
  +------+------------------+
  |      |                  |
Pocket1 Pocket2 ... PocketN (чанки текущего файла)
  |      |                  |
  +------+------------------+
        |
Упорядоченная сборка (строго по индексам чанков)
        |
sink (WAV/MP3/Opus): finish() отдельно от publish() (G5.1)
        |
Терминальное завершение файла -> СЛЕДУЮЩИЙ TXT (тот же пул)
```

Компоненты:

- `app-core/pipeline.rs::synthesize_stream_pooled` — конвейер одного файла
  на внешней фабрике воркеров с N параллельными чанками (обобщение
  `synthesize_stream_with_worker_factory` G6.6 с workers > 1);
  `build_file_tasks` — единый план чанков (чанкинг → ударения →
  char_rules → паузы) для конвейера и мультипроцессного диспетчера.
- `app-core/persistent.rs::pooled_real_worker_factory` + `PoisonLoan` +
  `live_slots`: воркер `run_job` одалживает любой свободный слот пула;
  per-file seed ставится перед первым чанком файла; сбой движка/паника
  `process()` отравляет слот (Pocket не возвращается в пул — классификация
  G6.1 перенесена внутрь займа); отмена Pocket НЕ травит (say_chunk
  пересеивает RNG на каждый чанк, детерминизм доказан P2B.2 §11).
- `gui/job.rs::execute_batch_chunk_pool` — каталог на однопроцессном пуле:
  файлы СТРОГО последовательно, чанки файла параллельно (min(C, живые
  слоты) воркеров `run_job`), существующие preflight/безопасность путей
  без изменений.
- `gui/chunkpipe.rs` — мультипроцессный чанк-конвейер (см. §4).

## 2. Определения P/W/C/T

- **P (processes)** — рабочие процессы с Pocket. При P=1 пул живёт в
  основном процессе приложения; при P>1 — в P дочерних процессах того же
  exe (`--internal-batch-worker`). Число P пользователь видит как «рабочие
  процессы» (GUI-диспетчер не считается).
- **W (workers_per_process)** — постоянных Pocket в каждом рабочем
  процессе; Pocket = 5 ONNX-сессий; создаётся один раз на задание и
  переживает файлы.
- **C (max_concurrent_chunks)** — верхний предел чанков текущего файла,
  находящихся в синтезе ОДНОВРЕМЕННО: `active = min(C, P×W, remaining)`.
  C не создаёт дополнительные Pocket. В однопроцессном пуле Pocket сверх
  C не создаются вовсе (`pockets = min(W, C)`); в мультипроцессе все P×W
  Pocket создаются (топологию задаёт память процессов), но диспетчер не
  выдаёт больше C чанков одновременно.
- **T (ort_threads)** — intra-op потоки ORT на одну ONNX-сессию.

`total_pockets = P × W`; файлов в обработке всегда ≤ 1. Диапазоны GUI:
CPU P 1..=4, CUDA P 1..=2, W 1..=4/1..=2, общий предел P×W ≤ 4 Pocket,
C 1..=P×W, T 1..=16.

## 3. Жизненный цикл Pocket и обработка каталога

1. `plan_batch` + `preflight_batch` (конфликты/пути/overwrite/reparse —
   без изменений G3/G6.1) ДО создания пула.
2. Пул создаётся один раз перед первым синтезируемым файлом
   (`spawn_workers`, параллельная загрузка, `Pocket загружен N раз(а)` —
   реальный счётчик в BatchReport).
3. Файлы обрабатываются строго последовательно: следующий TXT начинается
   только после терминального завершения предыдущего (Generating →
   Finalizing → Publishing → Completed/Failed/Skipped/Cancelled).
4. Pocket переиспользуются между файлами без перезагрузки (переход
   файл→файл ≈ 0 мс, замеры P2B.2); per-file seed — как в G6.1.
5. Сбой движка отравляет слот: файл Failed с диагнозом; при оставшихся
   живых слотах пакет продолжается меньшим числом воркеров (с явной
   записью в журнал); при полном отравлении оставшиеся файлы Failed
   («пул недостоверен») — повреждённое состояние движка не используется.
6. Ошибка чтения текста/sink/публикации Pocket не трогает.
7. После каталога пул освобождается (слоты опустошаются в потоках
   воркеров). Одиночный TXT — тот же механизм с пулом на один файл.

## 4. Мультипроцессный чанк-конвейер (P>1)

`gui/chunkpipe.rs`, гибридная инфраструктура G6.2 (Named Pipes duplex,
OVERLAPPED, проверка PID, Job Object KILL_ON_JOB_CLOSE, watchdog 300 с,
startup timeout 120 с, WRITE_WAIT_TIMEOUT, контролируемый shutdown —
без изменений).

- Дочерние процессы создаются один раз на задание; в каждом W постоянных
  Pocket (`worker_loop` загружает Pocket, Ready, живёт до Shutdown).
- Диспетчер владеет файлами: читает текст, строит `build_file_tasks`,
  создаёт sink, шлёт чанки командами `Cmd::AssignChunk{worker, pos,
  index, model_text, pause_s, seed}`; освободившийся воркер получает
  следующий разрешённый чанк.
- **IPC для PCM**: `Ev::ChunkDone{…, samples}` (JSON-заголовок) + один
  бинарный кадр `f32 little-endian` за ним. Оба кадра порождаются ОДНИМ
  сообщением writer-очереди дочернего процесса — перемешивание с событиями
  других воркеров невозможно. Большие PCM-массивы через JSON не идут.
  Выбор транспорта обоснован: Named Pipes уже верифицированы (G6.2.2a),
  кадр ≤ ~3 МБ (чанк ≤ ~30 с), накладные расходы минимальны, отмена и
  очистка наследуются от IPC жизненного цикла; отдельный канал/файлы/
  shared memory не потребовались.
- Результаты возвращаются в произвольном порядке; диспетчер собирает
  аудио СТРОГО по индексам чанков в буфере переупорядочивания и пишет в
  sink по порядку (`write_chunk(i, …)`), после всех чанков — фазы
  Finalizing/Publishing и публикация (единая точка решения G5.1).
- **Backpressure**: одновременно в работе ≤ C чанков; окно планирования —
  `next_assign < next_emit + C + 2` (ограниченное предпланирование, лимит
  C не обходит). Готовые-не-по-порядку чанки ограничены тем же окном —
  быстрые воркеры не синтезируют десятки будущих чанков из-за медленного
  раннего; всё аудио в памяти не накапливается.
- Seed: per-file seed назначает диспетчер; воркер ставит его на Pocket
  перед чанком; `say_chunk` пересеивает RNG как `seed + chunk_index` —
  аудио не зависит от того, каким Pocket/процессом выполнен чанк.
- Сбои: ошибка чанка → файл Failed, параллельные чанки этого файла
  дорабатываются и отбрасываются, следующий файл идёт штатно; ошибка
  движка → воркер WorkerError (Pocket отравлен), файл Failed; гибель
  процесса/разрыв IPC/watchdog → файл Failed с диагнозом, очередь
  доделывают выжившие; при полном отсутствии воркеров оставшиеся файлы
  Failed. Автоповторов нет.
- Отмена: стоп → диспетчер прекращает выдачу, `Cmd::Cancel` всем детям,
  чанки дорабатываются между итерациями движка, публикация дорабатывается
  по семантике G5.1, незапущенные файлы Skipped; shutdown с эскалацией
  только своих PID; сирот нет (Job Object проверен прежними E2E).

## 5. Профили

Кандидаты ТЗ G6.7 (совпадают с каноническими таблицами G6.6 численно, но
семантика C — чанки, не файлы):

| Параметр | CPU Оптимальный | CPU Производительный | CUDA Оптимальный | CUDA Производительный |
|---|---:|---:|---:|---:|
| P | 1 | 1 | 1 | 2 |
| W | 2* | 4* | 2 | 2 |
| C | =W | =W | 2 | 4 |
| T | 4 | 1 | 4 | 4 |

\* адаптируется: `clamp(floor(logical/4),1,4)` / `clamp(floor(logical/2),2,4)`
+ ограничение свободной RAM (~1.1 ГБ FP32 / 0.7 ГБ INT8 на Pocket, запас
1.5 ГБ). CUDA-префлайт VRAM сохранён (N×2355 МБ + 900/1500 МБ; авто-
деградация только у «Оптимального»; мультипроцесс при нехватке VRAM не
запускается — явный откат на однопроцессный пул с объяснением; fake-режим
пропускает). Ручная правка любого поля → профиль «Свой». Настройки CPU и
CUDA независимы; переключение режима/устройства ничего не сбрасывает.

ОДИН блок «Параллельная обработка» в разделе «Паузы и воркеры» для обоих
режимов (одиночный TXT и каталог) и обоих устройств: кнопки
[Оптимальный] [Производительный], строка «Режим: …», поля Процессов /
Воркеров на процесс / Одновременных чанков / Потоков ORT (ComboBox),

«Потоков ORT» одиночного режима, подсказка о чанк-воркерах в «Модель и
устройство». Компоновка/шрифты/тёмная тема G6.4 не менялись.

## 7. JSON и миграция

- `parallel_cpu` / `parallel_cuda`: поле переименовано
  `max_concurrent_files` → `max_concurrent_chunks`. При загрузке старый
  ключ переносится препроцессингом JSON ДО разбора (при наличии обоих
  приоритетен новый — дубль не ломает конфиг); при сохранении пишется
  только новый ключ. Семантика изменилась: предел файлов → предел чанков.
- P/W/T/профиль переносятся как есть; прежние миграции (batch_cuda_mode,
  `shtorm_gui_settings.json`) не менялись. Unknown-key round-trip, атомарная
  запись и защита повреждённых конфигураций — без изменений.
- Устаревшие `workers`/`threads` больше НЕ влияют на синтез: production
  берёт W и T только из parallel_cpu/parallel_cuda. Значения сохраняются
  для совместимости и используются исключительно диагностическим путём
  G6.6 (env, см. §9).

## 9. Диагностические пути G6.6 (не показываются в GUI)

- `SHTORM_GUI_G66_FILE_POOL=1` — прежний ФАЙЛОВЫЙ пул G6.6 (файлы
  параллельно, каждый целиком на одном Pocket; одиночный режим — «модель
  на задание»). Нужен для сравнения (бенчмарк §10) и не является
  пользовательским режимом.
- `SHTORM_GUI_BATCH_POOL=0` — последовательный пофайловый путь G3.
- Файловый мультипроцесс G6.2/G6.6 (`run_hybrid`) сохранён в коде и
  покрыт своими 24 E2E-тестами, но production-маршруты его не используют.

## 10. Производительность (G6.7 vs G6.6)

Корпус: 12 TXT × 4 чанка, 1×2/C2/T4, одинаковые модели/seed, один за другим
(бюджет тяжёлых прогонов ≤ 35 мин соблюдён; параллельные тяжёлые запуски
не выполнялись):

| Устройство | G6.7 (чанк-пул) | G6.6 (файловый пул) | Отношение |
|---|---:|---:|---:|
| CUDA | 35.7 с | 34.6 с | ×1.03 |
| CPU | 166.8 с | 159.0 с | ×1.05 |

G6.7 — сознательно выбранная архитектура (последовательные файлы), она на
3–5% медленнее файлового параллелизма на этом корпусе: файловый пул
перекрывает хвосты/финализацию соседних файлов, тогда как в G6.7 пауза
между файлами не заполняется. Возврата к параллельным файлам НЕТ. Первого
WAV G6.7 ждёт не дольше (пул стартует сразу с первого файла).

## 11. Безопасность отмены/публикации

Все гарантии G5.1/G6.2 сохранены: preflight до воркеров, уникальные
`.partial` + create_new, `finish()` отдельно от `publish()`, атомарная
замена только при overwrite, отмена до точки решения не публикует, после —
конвейер доходит до конца; ошибки файла/Pocket/процесса/IPC/watchdog
раздельны; автоповторов нет; Job Object — сирот нет; kill только своих
PID. G6.7: отмена между файлами не создаёт `.partial` у незапущенных
файлов (черновики сохраняются только у реально стартовавших — тест
real_batch_cuda_hybrid_cancel).

## 12. Известные ограничения

- Общий предел P×W — не более 4 Pocket (первая реализация, ТЗ §7).
- В мультипроцессе при C < P×W лишние Pocket создаются и занимают память
  (топология IPC); в однопроцессном пуле лишние Pocket не создаются.
- Лог чанков в мультипроцессном режиме пишет диспетчер без per-chunk
  метрик воркеров (времена/денойз агрегируются, строки чанков без
  worker_id/ms); в однопроцессном пуле лог полный.
- Время окончания файла — фактическое (после публикации), «Время
  перехода между файлами» ≈ 0 мс (переиспользование пула).
- CUDA: эффект C на ОДИНОЧНОМ TXT мал (latency-bound, P2B.2); выигрыш
  проявляется в каталоге и на CPU.
- Пресет «Оптимальный» CUDA может авто-деградировать по VRAM (с записью в
  журнал); ручные конфигурации не подменяются молча.
- Портативный комплект НЕ пересобирался (по ТЗ — только после ручной
  приёмки).
