## 1. Прежняя архитектура (G3, до G6.1)

`execute_batch` → `run_batch` (последовательный цикл по файлам плана) → на
каждый файл `execute_job` → `synthesize_stream` → `run_job`, который фабрикой
`real_worker_factory` создавал N воркеров (N = effective_workers: CPU 2 /
CUDA 1), распределял ЧАНКИ файла между ними и дропал воркеры в конце файла.
Стоимость: загрузка Pocket (≈1.4–2 с, 5 ONNX-сессий, ≈2.1 ГБ VRAM CUDA) на
каждый файл пакета.

Очередь K/N в UI была рассчитана на один активный файл: события
`FileProgress`/`FileDone` перезаписывали единственные поля
`file_progress`/`progress`.

## 2. Новая архитектура (G6.1)

Один процесс Rust. Для пакетного CUDA с ≥2 файлами-кандидатами:

```
execute_batch
  ├─ plan_batch (снимок файлов, конфликты имён — как раньше)
  ├─ preflight_batch  ← НОВОЕ: все предзапусковые решения ДО воркеров
  │    (конфликты → Skipped, unsafe-пути → Failed, существующий результат
  │     без overwrite → Skipped; каталоги создаются здесь же)
  ├─ решением count_actionable ≥ 2 && CUDA: постоянный пул
  │    ├─ spawn_workers(N) — N Pocket параллельно, один раз на пакет
  │    ├─ run_prepared_parallel → app-core run_dynamic_queue:
  │    │     общий AtomicUsize-счётчик; поток воркера берёт следующий файл,
  │    │     обрабатывает его ЦЕЛИКОМ (run_job workers=1), берёт следующий
  │    └─ Pocket освобождаются в потоках воркеров после пакета
  └─ иначе прежний последовательный путь (CPU, одиночный файл, откат)
```

Ключевые компоненты:

- `crates/app-core/src/persistent.rs` — переиспользуемое ядро:
  - `WorkerSlot<W> = Arc<Mutex<Option<W>>>` — слот постоянного воркера;
    `None` — занят файлом, отравлен или освобождён;
  - `Loaned<W>` — воркер, «одолженный» на файл: `Drop` возвращает его в слот
    (паттерн проверен diag_p2b2);
  - `loaned_worker_factory(slot, prepare)` — фабрика для
    `run_job(workers=1)`: берёт воркер из слота, прогоняет через
    `prepare(worker, seed)` (per-file seed!), возвращает `Loaned`;
    `loaned_real_worker_factory` ставит seed через `RealWorker::set_seed`;
  - `spawn_workers(n, factory, seed)` — параллельная загрузка N воркеров
    (каждый в своём потоке, паника/сбой загрузки — диагностика ЭТОГО воркера,
    повторов нет);
  - `run_dynamic_queue(slots, total, cancel, job)` — динамическая очередь:
    события файлов приходят из потоков воркеров вперемешку; паника `job`
    отравляет слот и записывает фатальную ошибку с позицией файла.
- `app_core::pipeline::synthesize_stream_with_worker_factory` — публичная
  обёртка `synthesize_stream` с инъекцией фабрики и `workers = 1`: файл целиком
  на одном внешнем Pocket. Вся математика (чанкер → char_rules → паузы →
  DSP → sink → publish) — та же функция `synthesize_stream_impl`, что и в
  одиночном режиме: дублей алгоритма нет.
- `gui/batch.rs`: `preflight_batch` (решения до воркеров),
  `run_prepared_parallel` (параллельный раннер на слотах пула),
  `run_prepared_sequential` (прежний путь; `run_batch` — обёртка для тестов).
- `gui/job.rs`: `execute_batch_persistent_pool` (подготовка движка один раз,
  preflight, подготовка путей, VRAM-префлайт, spawn, параллельный прогон),
  `execute_batch_file_persistent` (один файл на loan-воркере + отравление
  слота при ошибке движка), `decide_batch_pool_workers` (число воркеров).
- `gui/app.rs`: per-file модель UI (§7).

Диагностические бинари diag_p2b2/p2b3 не менялись (замеры P2B — frozen);
GUI использует те же проверенные примитивы, вынесенные в app-core.

## 3. Жизненный цикл Pocket

1. `spawn_workers` создаёт N Pocket параллельно (wall ≈ одной загрузки);
   параметры движка — из PipelineOptions, seed загрузки — стартовый (per-file
   seed ставится позже).
2. Воркер ждёт файл в очереди.
3. Файл: фабрика одалживания берёт Pocket из слота, ставит per-file seed
   (см. ниже), файл целиком синтезируется одним Pocket
   (`run_job workers=1` — порядок чанков и seed+index как в одиночном run).
4. `Loaned::drop` возвращает Pocket в слот — между файлами НЕТ ни загрузок
   модели, ни пересоздания ONNX-сессий (5 сессий на Pocket за весь пакет).
5. После исчерпания очереди/отмены поток воркера освобождает Pocket
   (`*slot = None`) — VRAM возвращается до выхода потока.
6. Отравление (poisoning): ошибка движка в файле или паника → слот
   опустошается и НЕ переиспользуется (§6).

**Per-file seed на постоянном Pocket.** `Pocket::say_chunk` пересеивает RNG
как `seed + chunk_index` на КАЖДЫЙ вызов, поэтому установка поля seed перед
первым чанком файла (`RealWorker::set_seed`) даёт поток, идентичный свежему
Pocket с этим seed. Seed разрешается на файл тем же правилом, что и раньше
(`opts.seed`; −1 → случайный НА ФАЙЛ) — фабрика получает его из конвейера.
Побитовый паритет переиспользования доказан P2B.2 §11 и подтверждён real-тестом
G6.1 (12 файлов побитово = пофайловому пути, включая 10 файлов на прогретых
Pocket).

## 4. Распределение файлов

Общая динамическая очередь (`AtomicUsize`): освободившийся воркер немедленно
берёт следующий файл. Никакого закрепления половины файлов за воркером.
Гарантии:

- ровно одно назначение на файл (fetch_add атомарен; в тестах — по `claimed`);
- относительная структура каталогов — как раньше (`output_path_for`);
- seed и состояние Pocket — независимы на файл (§3);
- порядок чанков внутри файла — строгий (run_job);
- потоковый аудиовывод — свой AudioSink на файл;
- потеря файла исключена: отчёт строится по ВСЕМ позициям плана, незапущенные
  при отмене → Skipped «отменено до запуска», при гибели воркеров → Failed
  (файл паники) / Skipped с явной причиной (остальные);
- итоговый отчёт — в исходном порядке плана (`reports[idx]`), хотя фактическое
  завершение может идти в любом порядке.

## 5. Семантика Cancel

«Стоп» в пакете (кнопка доступна, пока хотя бы один активный файл в фазе
Generating; между файлами — всегда доступна):

1. Общий cancel-флаг: диспетчер (claim-цикл) перестаёт выдавать файлы.
2. Активные файлы: `run_job` прерывает генерацию между чанками → статус
   Cancelled, публикация НЕ выполняется (точка решения G5.1 до финализации).
3. Файлы, уже перешедшие точку решения (Finalizing/Publishing), ДОРАБАТЫВАЮТ
   публикацию до конца — отмена одного публикующегося файла не блокирует
   отмену генерирующегося соседа (UI не отключает «Стоп», пока хоть один
   файл отменяем).
4. Все потоки присоединяются; Pocket освобождаются; сиротских ffmpeg нет
   (Drop/abort FfmpegSink); `.partial` и диагностические журналы сохраняются.
5. Ранее успешно опубликованные файлы остаются готовыми.
6. Итоговый статус — точные счётчики: Cancelled с «готово X | ошибок Y |
   пропущено Z» (не «всё отменено», если что-то успело завершиться).
7. Повторный запуск после отмены — штатный: готовое пропускается (overwrite
   выключен), остальное доделывается (real-тест: 1 готов + 11 доделано).

## 6. Поведение при ошибках

- Ошибка чтения текста / создания sink (ffmpeg, unsafe-путь) — сбой ФАЙЛА:
  Pocket не при чём, слот не трогается, остальные файлы продолжаются.
- Ошибка ONNX/движка в файле (StreamError без publish_failed) или паника в
  потоке воркера — Pocket может быть в неопределённом состоянии: слот
  ОТРАВЛЯЕТСЯ (Pocket освобождается и не переиспользуется как исправный).
  Остальные воркеры продолжают очередь (свои Pocket изолированы).
  Классификация консервативна в пользу безопасности: любой сбой, кроме
  публикации, отравляет слот — цена ошибки классификации лишь потеря одного
  воркера до конца пакета, обратное (переиспользование битого Pocket) могло
  бы портить результаты.
- Ошибка публикации (кодирование прошло успешно, publish_failed=true) —
  Pocket исправен, слот сохраняется; файл Failed, старый файл не изменён.
- Все воркеры погибли / не загрузились: файлы получают Failed/Skipped с
  диагнозом «пул не запущен»/«воркеры пула завершились» — задание не
  исчезает молча, пакет завершается с честным отчётом.
- Отказ загрузки пула (OOM и т.п.): частично созданные Pocket освобождаются,
  повторов загрузки нет, пакет НЕ начинается в неопределённом состоянии —
  все файлы-кандидаты Failed с диагнозом (real-поведение; см. §8 про
  префлайт, снижающий вероятность).
- Паника в фабрике/процессе чанка внутри run_job — существующая защита
  (catch_unwind → ошибка задания) → срабатывает отравление слота выше.

## 7. Безопасная публикация (без изменений семантики G5/G5.1)

Всё сохранено и выполняется НА ФАЙЛ в потоке его воркера:

- уникальный `.partial` на результат (`{stem}.{нс}.{pid}.{счёт}.partial.{ext}`);
- новая запись только по безопасному пути: `ensure_output_path_safe` ДО
  создания каталогов, `create_dir_all_no_reparse`, повторная валидация ПОСЛЕ
  (в пуле — на этапе preflight, ДО запуска воркеров);
- существующий файл без перезаписи → Skipped (решение в preflight), с
  перезаписью → атомарная замена только после успешного синтеза;
- `finish()` и `publish()` раздельны; после точки решения отмена не отзывает
  файл; старый файл цел при ошибке/отмене; черновики не удаляются;
- конфликтные имена (`chapter.txt` + `chapter.md`) исключаются в плане ДО
  запуска воркеров — два воркера физически не могут писать в один путь;
- каждый файл владеет своим AudioSink, путём результата, журналом и статусом;
  воркер не публикует чужой результат.

Проверено real-тестами на WAV/MP3/Opus (overwrite=false: побайтово целы;
overwrite=true: «файл обновлён», .partial не остаётся; §9).

## 8. Потребление VRAM и префлайт

Факт (соответствует P2B.3): 1/2 Pocket ≈ 2.8/4.9 ГБ (пик за пакет; ≈2.1 ГБ
на воркера + база). Перед созданием ≥2 CUDA-воркеров выполняется префлайт
`nvidia-smi memory.free` (порог: N×2355 + 900 МБ, как в launcher'е P2B.3):

- **авто** (workers не задан): 2 воркера; при нехватке — деградация до 1 с
  понятной записью в журнале;
- **ручной выбор**: число пользователя не игнорируется молча — при нехватке
  VRAM предупреждение в журнал, значение сохраняется; >2 — предупреждение
  по итогам P2B.2/P2B.3 (не ускоряет, ~2.1 ГБ на воркера);
- воркеров никогда не больше, чем файлов-кандидатов (лишние Pocket не
  грузятся);
- префлайт НЕ считается абсолютной защитой от OOM: реальная неудача загрузки
  завершает пакет с диагнозом (§6), автоматических повторов нет.

## 10. Производительность

Методика: набор main12; `real_batch_cuda_bench` — прежний пофайловый путь
(`SHTORM_GUI_BATCH_POOL=0`, 1 воркер на файл, 12 загрузок Pocket) против
постоянного пула 1/2 воркера; прогрев + 3 измеренных повтора на режим;
в процессе — сэмплер nvidia-smi (util/VRAM ~0.3 с) и CPU (PowerShell, реже).
Wall — полный прогон пакета (включая загрузки Pocket и создание пула);
аудио набора 454.0 с (речь 410.2 с + паузы).

- **pool2 против прежнего пути: −37.3% wall** (69.3 → 43.5 с), +59%

- Диапазоны повторов режимов не пересекаются; разброс 0.5–2.4%.

## 11. GUI

- Запуск пакета CUDA: авто 2 воркера (VRAM-префлайт может снизить до 1 —
  запись в журнале), ручной 1/2 — постоянные Pocket (1/2 загрузки на пакет).
- Прогресс: полоса «файлы K/N (готово X | ошибок Y | пропущено Z)» + строка
  на каждый активный файл («[K] имя — чанки d/t (генерация/сохранение)»);
  события параллельных файлов не перезаписывают чужие индексы (per-file
  модель `BatchUiState`, события `FileStarted/FileProgress/FilePhase/FileDone`
  несут индекс файла).
- «Стоп» учитывает фазы всех активных файлов (§5); журнал — как раньше.
- Одиночный режим и CPU-пакеты — прежний путь без изменений.

Проверка реальным exe: headless-режим `--portable-selftest-batch` с
настроенным CUDA — пул 2 воркера, ровно 2 загрузки Pocket, 2/2 готово
(§9). **Полной визуальной проверки живого окна на идущем пакете не
выполнялось**: пользователь открывал окно с остаточными тестовыми
настройками (пустые текст/голос — валидация внизу честно это показала);
прогресс нескольких файлов/Стоп в живом окне подтверждены модельно
(unit-тесты apply_event/BatchUiState) и headless-прогоном, но не глазами.
Примечание к инциденту проверки: флаг selftest —
`--portable-selftest-batch` (НЕ `--portable-batch-selftest`: неверное имя
молча открывает GUI-окно).

## 12. Известные ограничения

- Многопроцессный режим 2×2 (G6.2) не реализовывался; IPC не вводился.
- Полная визуальная проверка живого окна на идущем пакете не выполнялась
  (§11); headless-exe и модельные тесты — зелёные.
- CPU-пакеты остаются на пофайловом пути (не тестировалось на пуле — явное
  ограничение задания G6.1; перевод CPU на пул — отдельное решение).
- Пакет из одного файла идёт прежним путём (мульти-воркерное распределение
  чанков); эквивалент по поведению, Pocket загружается на файл.
- `SHTORM_GUI_BATCH_POOL=0` — недокументированный в UI диагностический откат
  на прежний путь (использован бенчмарком и паритет-тестом).
- VRAM-префлайт — эвристика (порог P×2355+900 МБ), не гарантия от OOM;
  гонка с внешними потребителями VRAM между префлайтом и загрузкой остаётся.
- Случайный seed (−1): в пуле seed разрешается на файл так же, как раньше
  (Random.resolve на файл); но воркеры пула создаются со стартовым seed —
  до первого файла per-file seed гарантированно установлен фабрикой.
- Отравление слота после ошибки движка — консервативное: файл со сбоем
  ffmpeg (ошибка приёмника) тоже отравляет слот (безопасность важнее одного
  воркера; publish_failed — исключение).
- Диагностические бинари diag_p2b2/p2b3 сохранены как есть (замеры P2B
  воспроизводимы); их оркестрация НЕ переведена на persistent.rs.

## 13. Подготовка к G6.2 (гибрид 2×2)

Основа готова: динамическая очередь и preflight независимы от числа
процессов; для 2×2 потребуется IPC-слой (запуск/отмена/журналы второго
процесса, claim-очередь между процессами — прототип в diag_p2b3), VRAM-префлайт
с порогом ≥ ~10.3 ГБ и откатом на 1×2, слияние отчётов двух процессов в
исходном порядке. По заданию G6.1 — НЕ начинать без отдельного задания.
