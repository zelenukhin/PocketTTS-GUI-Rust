# SAFETY_AUDIT — устранение деструктивных операций (после инцидента 2026-11-08)

Дата: 2026-11-08. Базовый коммит: `bf4e9da` (этап выполнен поверх, история не
переписывалась). Приоритет этапа — безопасность существующих файлов; A3 не
начинался, бенчмарки и CUDA-эксперименты не выполнялись.

## 1. Первопричина инцидента

При проверке фикса №1 прошлого этапа запускались «негативные тесты» утилиты
`ep_probe` с `--trace-dir`, указывающим на корень проекта и домашний каталог.
Гвард первой версии сравнивал результат `canonicalize()` (на Windows — путь с
префиксом `\\?\`) с обычным путём — сравнение всегда давало «не совпадает»,
гвард молча пропускал защищённые пути, и `remove_dir_all` приступал к
реальному рекурсивному удалению. Удаление остановилось только на файлах,
занятых процессами.

Последствия: безвозвратно удалены скрытые каталоги профиля пользователя
(`.cargo`, `.rustup`, `.gitconfig`, `.ssh`, `.gnupg`, `.config` и др.; выжил
занятый `.zcode`), корень проекта (`crates/`, `Cargo.toml`, `.git` с историей)
и `deps/ort-cpu`. Видимые данные (Documents/Downloads/Desktop, модели,
Python-проект) уцелели. Проект был восстановлен из сетевых копий, тулчейн —
переустановлен.

**Процессная причина**: после первого же падения гварда был запущен второй
деструктивный тест на живом пути вместо остановки. Правило, зафиксированное
настоящим этапом: негативные тесты вообще не выполняются на реальных путях —
только изолированные песочницы и чистая логика.

## 2. Почему прежний гвард был недостаточен

1. **Ложное сравнение путей**: `\\?\C:\...` (canonicalize) ≠ `C:\...` — все
   проверки «совпадает с защищённым» всегда проваливались.
2. **Модель «сначала проверить, потом удалить» принципиально ненадёжна**:
   любой баг проверки немедленно превращается в удаление чужих данных.
   Белый список содержимого каталога не спасает, если сам каталог выбран
   неверно, а порядок проверок зависит от деталей реализации.
3. **Сами негативные тесты были деструктивными**: тест
   `refuses_foreign_files_allows_own_traces` удалял фиксированный каталог в
   `%TEMP%` — шаблон, который при ошибке гварда повторял инцидент.

Вывод: единственный безопасный уровень защиты — **полное отсутствие
рекурсивных удалений в кодовой базе**. Диагностика создаёт новые файлы и
каталоги, ничего не очищая; удаление — всегда ручная операция пользователя.

- **Необратимость уже потерянного**: `.ssh`/`.gnupg` и прочие скрытые
  каталоги профиля, удалённые в инцидент, этим этапом не восстанавливаются;

- TOCTOU-окно между `exists()`-проверкой и созданием файла в smoke/bench
  (микроскопичное, путь выбирает оператор).
- Генераторы golden и plot_memory перезаписывают фиксированные файлы внутри
  проекта — осознанное исключение (регенерация), задокументировано.
- Тесты и смоуки оставляют артефакты в `%TEMP%` (каталоги
  `shtorm_tracedir_*`, тестовые wav) — плата за политику «без удалений»;
  чистка — вручную пользователем.
- Пользователь по-прежнему может передать инструментам путь с записью в свои
  каталоги (`--out`, `--csv`, `--trace-dir`): инструменты не удаляют ничего
  существующего, но создание новых файлов в указанном месте — штатное
  поведение, контролируемое оператором.

## Дополнение A5.1 (2026-11-09): публикация, уникальные черновики, отмена

1. **Публикация результата — Win32 `MoveFileW` без MOVEFILE_REPLACE_EXISTING**
   (function `audio_processing::stream::publish_no_replace`): при занятом
   имени назначения вызов атомарно отказывает, назначение не меняется,
   черновик сохраняется. После успешного переноса `.partial` больше нет
   (перемещён, не удалён). NTFS — проверено юнит-тестами (отказ при
   существующем файле с проверкой содержимого обеих сторон). **exFAT —
   не проверялся** (в системе нет exFAT-носителя; семантика Win32 API не
   зависит от ФС, но это остаётся подтверждением только на уровне API).
   На не-Windows платформах — `hard_link` (fail-if-exists) + удаление
   собственного черновика.
2. **Уникальные черновики за запуск**: `{stem}.{нс}.{pid}.{счётчик}.partial.{ext}`
   (наносекунды + атомарный счётчик). Повторный запуск с тем же итоговым
   именем возможен; старые черновики НЕ удаляются автоматически и не мешают.
3. **FFmpeg stderr** читается до EOF (дренаж pipe) с сохранением только
   ограниченного хвоста (8 КиБ) — устранён риск дедлока при объёме
   диагностики > 64 КиБ; проверено дочерним процессом-производителем
   128 КиБ с внешним таймаутом 60 с.
4. **Жизненный цикл FFmpeg**: `abort()` — закрыть stdin, дать штатно
   завершиться (лимит 5 с), при необходимости убить ТОЛЬКО свой дочерний
   процесс, всегда `wait()` + join потока stderr; `Drop` вызывает abort как
   защиту. Черновик при отмене/ошибке сохраняется и его путь сообщается.
5. **Ctrl+C в CLI**: флаг отмены (без process::exit в середине работы),
   статус Cancelled, итоговый файл не публикуется, пишется отдельный
   диагностический журнал с эксклюзивным именем
   (`{stem}.{нс}.{pid}.diagnostic_log.txt`), exit code 2. Ошибки задания —
   типизированный StreamError (прогресс, seed, путь черновика) и
   диагностический журнал; exit code 1.
6. Политика «без рекурсивных удалений» сохранена: в коде по-прежнему нет
   remove_dir_all; тесты не удаляют файлы (черновики остаются в %TEMP%).

На этом этапе реальные пользовательские файлы не удалялись и не
перезаписывались; проверки проводились в уникальных каталогах %TEMP%.
