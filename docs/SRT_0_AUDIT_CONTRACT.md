## 1. Таблица переноса Python → Rust

| Функция Python | Назначение | Аналог Rust | Перенос / замена |
|---|---|---|---|

| `_collect_srt_subtitles` | Чтение SRT → реплики с чанками; пустые остаются без чанков | `srt_parse.rs` + планировщик SRT (существующее чанкование Standard/Android) | ПОРТ семантики; границы реплик — приоритет над чанкером (см. §4) |
| `_build_srt_tasks` | Задачи воркерам: чанк → WAV-файл | плоский список `Task` в существующий пул (`pool::run_job`) | ЗАМЕНА: без файлов, PCM возвращается пулом в память |
| `_concat_subtitle_parts` | Склейка чанков реплики с паузами 500/100 мс | SRT-сборка PCM в памяти + внутренние паузы (см. §6) | ЗАМЕНА: без concat_list.txt/FFmpeg concat |
| `_assemble_srt_track` | Выравнивание таймингов + склейка трека | `app-core/src/srt.rs::SrtTimingPlanner` + потоковая запись в `AudioSink` | ПОРТ алгоритма дословно (§8); финальная склейка — потоковый sink (§9) |
| `_write_srt_timing_log` | Лог таймингов `{имя}_log.txt` | Rust-аналог в SRT-оркестраторе (create_new, как `write_chunk_log`) | ПОРТ формата |
| `_process_one_srt` | Цикл файла: синтез → выравнивание → сборка | SRT-оркестратор на постоянном пуле воркеров | ЗАМЕНА архитектуры Python (без временных папок/процессов) |

**Из Python НЕ переносится** (по ТЗ): управление моделями PyTorch, xVibe,

перезапуск воркеров, `paragraph_pause_ms` (см. §6.3), MP3 как единственный
альтернативный формат (в Rust — WAV/MP3/Opus).

## 2. Ответы на контрольные вопросы ТЗ (раздел 2)

1. **Чтение/валидация SRT.** Python: `utf-8-sig` (BOM съедается),
   `errors='replace'`, содержимое `.strip()`, блоки по `\n\s*\n`,
   таймкод ищется в строке 0 или 1 блока, индекс — `int` строки 0
   (при её отсутствии/не-числе — последовательный номер), текст — строки
   после таймкода, пустой текст → блок пропускается, итог сортируется
   **по индексу**. Валидации таймкодов, хронологии, дублей, перекрытий
   в Python НЕТ. Rust: парсинг дословно + предупреждения (§3).
2. **Очистка.** `{\...}` → пробел; HTML-теги `</?[A-Za-z]...>` → пробел;
   `html.unescape` (двойные/именованные/десятичные entities);
   `\u00a0` → пробел; `[^\S\n]+` → одиночный пробел (переводы строк
   сохраняются — по ним режутся абзацы); `\n{3,}` → `\n\n`; `strip(" \n")`.
   Порядок именно такой: теги → сущности → пробелы.
3. **Разбиение длинных реплик.** Python: `chunk_text` с байтовым лимитом
   `max_tokens×2×2`; приоритеты: абзацы → конец предложения → `:;—` →
   запятая → союз «и» → пробел у середины. Rust: существующий выбранный
   в настройках чанкер (Standard=`max_tokens` / TeraTTS Android=
   `max_chunk_chars`), применяемый К КАЖДОЙ реплике отдельно; чанк никогда
   не объединяет текст двух реплик (границы SRT — приоритет).
4. **Сборка реплики из чанков.** Чанки реплики идут в пул как отдельные
   задачи, возвращаются строго по порядку; PCM чанков соединяются в буфер
   реплики с внутренними паузами (§6); последний чанк реплики — без паузы.
5. **Обрезка тишины.** Каждый чанк уже обрезается в воркере
   (`trim_edges` 0.02/0.10 + `fade_out` 10 мс — действующий Rust-DSP,
   аналог Python-обрезки частей до склейки). Собранная реплика
   обрезается `trim_edges` повторно (аналог Python-обрезки в
   `_assemble_srt_track`) перед замером длительности.
6. **Фактическая длительность.** Число сэмплов соборанного PCM (u64),
   24 000 Гц: `ms = samples / 24` без потерь (частота кратна — политика
   конвертации мс↔сэмплы точная, дрейфа округления нет).
7. **Тишина до начала.** Если `start − track > 20 мс` — вставляется
   тишина на ВСЮ разность (допуск 20 мс сохранён из Python: порог
   срабатывания, а не вычет).
8. **Заимствование.** `borrow = max(0, next.start − end − min_pause_ms)`,
   где next — следующая реплика СПИСКА (включая пустые без чанков);
   последняя реплика — borrow = 0.
9. **Коэффициент ускорения.** При `raw > allowable`:
   `target = max(allowable, raw / max_tempo)`, `tempo = raw / target`.
10. **Ограничение.** `1.0 < tempo ≤ max_tempo` гарантировано полом
    `target`; замедление никогда (ветка ускорения не выполняется при
    `raw ≤ allowable`). Если времени мало даже на максимуме — слова не
    обрезаются, потолок не превышается, реплика опаздывает (честно
    фиксируется в логе таймингов и статусе).
11. **Учёт фактической длительности.** После SoundTouch длина берётся из
    реального числа полученных сэмплов (включая flush-хвост);
    `track += actual`. Расчётный tempo не используется для позиции трека.
12. **Перекрытия.** Python не проверяет: `pause_needed ≤ 0` → тишина не
    вставляется; `target = end − track` мал/отрицателен; срабатывает
    жёсткий лаг (п. 12a). Rust: то же поведение + предупреждение парсера.
    12a. **Жёсткий лаг (дословно из Python):** если
    `allowable < 100 мс` (2400 сэмплов), допустимое заменяется на
    `raw / max_tempo`. Следствие (quirk Python, сохранён): реплика,
    влезающая в окно < 100 мс, ускоряется до максимума. Документировано
    и покрыто тестом.
13. **Пустые реплики и ошибки.** Пустые после очистки — остаются в списке
    без чанков (тайминги участвуют в расчёте пауз; их «окно» поглощается
    тишиной до следующей озвучиваемой). Ошибка синтеза чанка в Python
    молча пропускала реплику; в Rust ошибка чанка останавливает файл
    (действующая семантика пула — задокументированное расхождение:
    частичная озвучка молча хуже явной ошибки).
14. **Настройки Python, реально используемые в SRT:** голос, температура,
    max_tokens (лимит чанков), decode_steps, EOS, frames_after_eos,
    char_rules, detect_truncation, seed, устройство, число процессов,
    `pause_ms` (внутренняя пауза, дефолт 500), `comma_pause_ms` (мягкая
    граница, дефолт 100), `max_tempo_increase` (2.0), `min_pause_ms`
    (100), split_sentences/ellipsis_sentences, формат (MP3/WAV),
    chunk_log (лог таймингов). **`paragraph_pause_ms` фактически НЕ
    действует**: передаётся воркерам, но пауза абзаца ставится только при
    `is_last_in_paragraph`, а SRT-сборка принудительно ставит всем чанкам
    `is_last=False` (`pocket-tts-srt_gui.py:1815`,
    `synthesis_worker.py:767`). В Rust-версии параметр НЕ переносится.

## 3. Контракт парсера (SRT.1)

Модуль `crates/text-processing/src/srt_parse.rs`. Чистые функции без
зависимостей от движка.

- `struct SubtitleCue { index: usize, start_ms: u64, end_ms: u64, text: String }`
  — `index` — исходный номер блока (для сортировки и диагностики);
  последовательная позиция (`pos`) присваивается отдельно после
  сортировки, хранение раздельно (ТЗ).
- `fn parse_srt(content: &str) -> SrtParseResult { cues: Vec<SubtitleCue>, warnings: Vec<String> }`.
  Поведение дословно как Python (кодировка/BOM — обязанность вызывающего:
  чтение файла в GUI-слое, `utf-8-sig` эквивалент — пропуск BOM,
  битые байты — replacement-символ).
- `fn strip_srt_tags(text: &str) -> String` — порт §2.2.
- **Сортировка — по `index` (политика Python, сохранена)**, стабильная.
  Хронология НЕ переупорядочивается молча.
- **Предупреждения (не фатально):** `end_ms <= start_ms`; дубликаты
  индексов; нарушение хронологии (`start[i+1] < end[i-1]`-типа —
  перекрытия; убывающие `start`); подозрительная длительность
  (> 60 с). Обрабатываются как Python (значения используются как есть),
  предупреждения попадают в журнал GUI и notes плана.
- **Фатально:** пустой результат (нет ни одного валидного блока с
  таймкодом) — явная ошибка чтения файла. Некорректный таймкод внутри
  блока → блок пропускается как в Python, с предупреждением.
- Таймкоды `HH:MM:SS,mmm` и `HH:MM:SS.mmm`; часы/минуты/секунды —
  ровно 2 цифры, мс — ровно 3 (regex Python); `-->` с пробелами вокруг.

## 4. Контракт чанкования реплик

- Реплика чистится `strip_srt_tags`; пустая → без чанков (остаётся
  в списке).
- Непустая → существующий чанкер **per-subtitle**:
  - Standard: `chunk_pipeline(clean, max_tokens)` — те же тексты,
    тот же `soft_break`/`is_last`; последний чанк реплики теряет
    статус последней (пауза после реплики не ставится никем).
  - TeraTTS Android: `android_chunk_pipeline(clean, opts)` per-subtitle;
    `pause_s` последнего чанка реплики → None (аналог `.last=None`
  в `build_file_tasks`); сцены/пропуски внутри реплики — по действующей
    семантике; отброшенные чанки переносят паузу в предыдущий.
- Чанк никогда не содержит текст двух реплик; реплика может иметь
  много чанков; текст репликки не дублируется и не теряется
  (инвариант паритета текстов как в TXT-планировщике).

## 5. Контракт DSP и обрезки

- Воркер не меняется: `say_chunk` → brightness → denoise →
  `trim_edges(0.02, 0.10, 24000)` → `fade_out(10 мс)`. Это обрезка
  каждого ЧАНКА (аналог Python-обрезки частей до склейки).
- SRT-сборщик после соединения чанков реплики с паузами применяет
  `trim_edges` К РЕПЛИКЕ (аналог `trim_wav_edges(raw_path)` в
  `_assemble_srt_track`) и замеряет `raw_samples`.
- Никаких других преобразований PCM до SoundTouch нет.

## 6. Контракт внутренних пауз (слои не дублируются)

| Слой | Владелец паузы | Значение |
|---|---|---|
| Воркер DSP | нет пауз | только обрезка краёв чанка |
| SRT-сборка реплики | Standard: плоская политика SRT — `soft_break` → `srt_comma_pause_ms` (дефолт 100), иначе `srt_internal_pause_ms` (дефолт 500); последний чанк реплики — всегда без паузы | совместимость с Python-дефолтами 500/100 |
| SRT-сборка реплики | Android: `pause_s` метаданные чанкера (стыки ≥0.02, aside 0.25, хвосты знака×scale, сцены 1.3×scale) — единственный источник | без наложения 500 мс |
| Timing planner | тишина до `start_ms` реплики (порог 20 мс) | §8 |
| AudioSink | никто: все реплики пишутся с `pause_s = None` | пауз в sink-слое нет |

Обоснование: Python SRT использует плоские 500/100 (не
пунктуационные `trailing_pause_s` TXT-режима); Standard-чанкер уже
размечает `soft_break` — этого достаточно. Android-режиме запрещено
выводить паузы из последнего символа — используются готовые метаданные.
GUI: ползунки внутренних пауз активны только в Standard-режиме
чанкования; в Android — заблокированы с подсказкой.

3. `paragraph_pause_s` НЕ применяется нигде в SRT-пути (подтверждено §2.14).

## 7. Контракт SoundTouch (SRT.3)

- **Библиотека**: SoundTouch **2.4.1** (codeberg/surina.net, tarball
  `soundtouch-2.4.1.tar.gz`, SHA256 фиксируется в docs и манифесте).
- **Компоновка**: динамическая `SoundTouchDLL.dll` (официальный C-обёртка
  `source/SoundTouchDLL`), собранная MSVC x64 (`cl /LD /O2 /EHsc /MD
  /std:c++17 /DDLL_EXPORTS`, все 14 .cpp SoundTouch + SoundTouchDLL.cpp;
  пробная сборка проверена: экспорты `soundtouch_*` на месте, x64).
- **Rust-обёртка**: `crates/app-core/src/soundtouch.rs`, runtime-загрузка
  `LoadLibraryW` + `GetProcAddress` (в PE-импортах EXE SoundTouch
  ОТСУТСТВУЕТ). Обычные EXE не зависят от DLL ни в сборке, ни в рантайме.
  Резолв пути: exe-relative (как остальные ресурсы) → стандартный поиск.
  Отсутствие DLL/функций — явная ошибка SRT-задания.
- **Параметры речи** (проверены по исходнику 2.4.1, main.cpp:126–133,
  эквивалент `-speech`): `SETTING_SEQUENCE_MS=40`, `SETTING_SEEKWINDOW_MS=15`,
  `SETTING_OVERLAP_MS=8`; AA-фильтр включён (умолчание), QUICKSEEK
  выключен (умолчание). `setTempo` (НЕ `setRate`/`setPitch`).
- **Потоковый протокол на реплику**: createInstance → setSampleRate(24000)
  → setChannels(1) → setSetting(×3) → setTempo(ratio) → putSamples(f32)
  блоками → receiveSamples до осушения → flush() → receiveSamples до
  пустого → destroyInstance. Состояние между репликами не переносится
  (новый instance на реплику — как новый процесс soundstretch.exe).
- **tempo = 1.0 → SoundTouch не вызывается** (исходный PCM без артефактов).
- Выходная длительность = фактически полученные сэмплы; NaN/Inf
  проверяются (защита от битой DLL — явная ошибка).
- **Лицензия LGPL 2.1**: динамическая компоновка (§4 LGPL); в комплект
  поставки входят DLL, `LGPL-2.1.txt`, уведомление и точный исходник
  (tarball) + скрипт сборки. Исходники проекта не заражаются LGPL —
  обёртка вызывает DLL по C-API.
- Побитовое равенство с soundstretch.exe НЕ является критерием (другая
  версия/параметры/конвертации); сравниваются длительности (±допуск) и
  аудиометрики.

## 8. Контракт Timing Planner (SRT.2)

Чистый модуль `crates/app-core/src/srt.rs`, без ONNX/SoundTouch.
Вход: список реплик (start/end в сэмпллах u64, флаг «есть чанки»),
`max_tempo: f32` (1.1..=3.0, дефолт 2.0), `min_pause_ms: u32`
(0..=500, дефолт 100). Всё в сэмпллах 24 кГц (1 мс = 24 сэмпла —
конвертация точная, накопления ошибки нет: ТЗ-кейс «многочасовой SRT»).

```
track = 0 (u64)
для каждой реплики i с PCM (raw_samples):
  target       = end_i.sat_sub(track)                 // шаг 2
  pause_needed = start_i - track (i64)
  если pause_needed > 480:                            // 20 мс
     emit тишина pause_needed; track += pause_needed
     target = end_i - track
  borrow = если есть next (реплика СПИСКА, включая пустые):
             max(0, next.start - end_i - min_pause)   // шаг 3
           иначе 0
  allowable = target + borrow
  если allowable < 2400:                              // 100 мс, жёсткий лаг
     allowable = raw_samples / max_tempo
  если raw_samples > allowable:
     min_possible = raw_samples / max_tempo
     target_dur  = max(allowable, min_possible)
     tempo       = raw_samples / target_dur           // 1.0 < tempo ≤ max
     emit PCM через SoundTouch(tempo); actual = получено сэмплов
  иначе:
     tempo = 1.0; emit исходный PCM; actual = raw_samples
  track += actual
  диагностика строки (§8.1)
```

- Отрицательный `target` невозможен как u64 — `sat_sub`; семантика
  эквивалентна Python (отрицательный allowable всегда < 100 мс →
  жёсткий лаг).
- Реплики без чанков не эмитируют ничего (тишина до следующей
  озвучиваемой покроет их окно).
- `min_pause_ms`/`max_tempo` применяются как в Python: замедление
  отсутствует; слова не обрезаются; опоздание честно фиксируется.

### 8.1. Диагностика на реплику (лог таймингов)

Номер, start/end, фактическое начало в треке, raw длительность,
допустимая длительность, заимствовано, применённый tempo, итоговая
длительность, фактический конец, опоздание относительно end,
причина (tempo на потолке). Формат — порт `_write_srt_timing_log`
(`{имя}_log.txt`, create_new, включается чекбоксом как в TXT).

## 9. Контракт потоковой записи (SRT.4–SRT.5)

- Переиспользуются `make_sink_with_overwrite` / `WavSink` / `FfmpegSink`
  без изменений: один sink на файл, PCM f32 mono 24 000, публикация
  `.partial` → `finish()` → `publish()` — семантика G5.1 (единая точка
  решения) сохранена.
- SRT-оркестратор пишет в sink последовательность:
  `тишина до начала → PCM реплики`, каждая запись — `write_chunk(idx,
  &pcm, None)`. FFmpeg запускается ОДИН раз на файл (существующий sink).
- Отмена: пул останавливается между чанками; до точки публикации файл
  не публикуется, `.partial` остаётся — как в TXT.
- **Память**: в RAM одновременно — PCM одного чанка (воркер) + буфер
  текущей реплики + окно пула (queue_cap+workers чанков). Предел буфера
  реплики: 15 мин × 24 кГц × f32 ≈ 86 МБ; превышение — явная ошибка
  (защита от аномалий). Весь трок в RAM не накапливается (sink — поток).
- Оркестрация: `run_job` существующего пула; SRT-сборщик — замыкание
  приёмника, собирающее реплики строго по порядку. Прогресс — чанки K/N.

## 10. Контракт GUI (SRT.6)

- Два новых бинарника: `PocketTTS-GUI-Rust-srt` (glow) и
  `PocketTTS-GUI-Rust-srt-cpu` (sw) — те же feature-наборы, общий код
  `gui`-крейта; `AppFlavor { Text, Srt }` в `ShtormApp`.
- Окно: «PocketTTS-GUI-Rust — SRT». Источник: `.srt` файл или папка
  (рекурсивно `.srt`); `.txt` не принимает. Настройки — все действующие
  (модель/голос/CPU-CUDA/FP32-INT8/генерация/анти-повторы/denoise/
  brightness/чанкование/P-W-C-T/формат/прогресс/журнал/Stop/
  автосохранение) + блок SRT:
  - «Максимальное ускорение» ×1.1..×3.0, дефолт ×2.0;
  - «Минимальная пауза между репликами» 0..500 мс, дефолт 100;
  - «Внутренняя пауза при разбиении» (Standard only; 500/100 мс
    дефолты, см. §6).
- Конфиг: `PocketTTS-GUI-Rust-srt.json` (оба SRT EXE — один файл);
  обычный `PocketTTS-GUI-Rust.json` SRT-версией не трогается.
  SRT-поля (`srt_max_tempo`, `srt_min_pause_ms`, `srt_internal_pause_ms`,
  `srt_comma_pause_ms`) добавлены в `GuiSettings` с serde-default —
  в обычном конфиге появляются со значениями по умолчанию, миграция и
  unknown-key round-trip действуют как раньше.
- Пакет: файлы строго последовательно, чанки текущего файла — на
  постоянном пуле (как `execute_batch_chunk_pool`); переиспользуется
  decide_topology без изменений.

## 11. Критерии приёмки этапов

- SRT.1: golden-тесты парсера (13 кейсов ТЗ §12.A) без движка.
- SRT.2: 13 кейсов ТЗ §12.B на синтетических длительностях.
- SRT.3: кейсы ТЗ §12.C (tempo 1.0/1.1/1.5/2.0, flush, изоляция
  реплик, NaN, 24 кГц mono).
- SRT.4: WAV/MP3/Opus одним sink-инстансом, cancel, ошибка энкодера —
  без готового файла; регрессии TXT-пути зелёные.
- SRT.5: паритет плана чанков с TXT-режимом (те же чанкеры), порядок
  реплик, `cargo test` workspace зелёный, FP32-путь не изменён.
- SRT.6: headless-тесты кадров SRT-режима, конфиг-изоляция.
- SRT.7/SRT.8: real CPU/CUDA, portable-набор с SoundTouchDLL.dll +
  лицензиями.

## 12. Известные ограничения / осознанные расхождения

1. Жёсткий лаг < 100 мс сжимает даже влезающие реплики до максимума —
   quirk Python, сохранён (тест-фиксация).
2. Ошибка синтеза чанка = ошибка файла (Python молча пропускал реплику).
3. Обрезка краёв — алгоритм проекта (`−45 дБ/5 мс hop`), не librosa
   top_db=70: числа длин краёв могут отличаться от Python; это
   действующий DSP проекта (ТЗ: существующие DSP-операции).
4. SoundTouch tempo — прямой f32-коэффициент, а не проценты `%.2f`
   soundstretch: точность выше, длительности всё равно фактические.
5. Перекрывающиеся реплики не переупорядочиваются и не растягиваются —
   предупреждение + поведение Python.
6. `split_sentences`/`ellipsis_sentences`-режимы Python в Rust
   покрываются выбором чанкера (Standard/Android); отдельные флаги не
   переносятся.
