# SRT.9 — исправление надёжности SRT-конвейера перед portable-релизом

Корректирующий этап по итогам дополнительного аудита исходников SRT.0–SRT.8.
Задача — устранить три потенциально опасных места БЕЗ изменения функционального
поведения: (A) поздняя проверка лимита PCM-памяти реплики, (B) обход каталогов
SRT по ссылкам, (C) соответствие SoundTouch FFI фактическому C ABI. Коммиты:
`8689e8a` (9A), `135cb88` (9B), `57f1c9f` (9C), финальный — 9D (тесты/доки).
База: `d0233f4` (SRT.8); NAS-бэкап ДО изменений:
`ShtormTTS-Windows-full-d0233f4-20261119.zip` (SHA256 `2F961E0C…DA314`,
231 entries, CRC OK).

## A. PCM-память реплики (SRT.9A)

### Исходная проблема

`crates/app-core/src/srt_pipeline.rs`, `SrtAssembler`:
`on_chunk()` расширял буфер реплики (`extend_from_slice` PCM-блока и `resize`
внутренней паузы) БЕЗ проверки лимита; единственная проверка
`max_cue_pcm_samples` находилась в `finish_cue()` — ПОСЛЕ накопления всей
реплики и обрезки краёв. При аномально длинной реплике (например, битый SRT с
одной многочасовой репликой или зацикленная подача чанков) буфер мог расти
неограниченно до момента финальной проверки.

Точное место до исправления: `on_chunk` — безусловно
`self.cue_pcm.extend_from_slice(pcm)` и
`self.cue_pcm.resize(self.cue_pcm.len() + pause as usize, 0.0)`;
проверка — в `finish_cue` по `trimmed.len()`.

### Репродукция (прогон тестов ДО фикса)

- лимит 2000, чанки по 600 сэмплов (паузы 500 мс): буфер дорастал до
  **177 000** сэмплов (88× лимита) до ошибки «слишком длинная ПОСЛЕ синтеза»;
- лимит 2000, паузы 0: накопление до 9000 (4,5×) перед ошибкой;
- 6 новых тестов падали на старом коде с сообщением поздней проверки.

### Новый инвариант

Лимит действует **до накопления**: `ensure_cue_capacity(cur, add, limit,
cue_index)` проверяется ПЕРЕД `extend_from_slice` входного блока и ПЕРЕД
`resize` внутренней паузы (пауза — часть буфера реплики и не может вытолкнуть
его за предел). Арифметика безопасна: `u64::checked_add` (переполнение —
явная ошибка «переполнение счётчика сэмплов»), `usize::try_from` (ошибка
платформы на 32-бит при need > usize::MAX), без копирования входных данных
ради проверки. Превышение — понятная ошибка
`реплика [N] превышает ограничение PCM-буфера: требуется X сэмплов, разрешено Y`
(без обрезания звука, без автоповышения лимита, без аллокации до отказа);
ошибка сборщика останавливает пул (`sink_error` в `run_job`) → файл НЕ
публикуется, `.partial` остаётся для диагностики (G5.1).

Страховочная проверка в `finish_cue` (после `trim_edges`) сохранена — при
соблюдении инварианта недостижима (обрезка только укорачивает), удалена третья
копия: `drop(pcm)` сразу после `trim_edges`.

### Учёт внутренних пауз и переполнений

Паузы учитываются в той же проверке (см. тест 5: 600 PCM + 12000 пауза при
лимите 2000 → ошибка до `resize` с «требуется 12600»). Граничные значения
u64/usize покрыты юнит-тестом `capacity_check_arithmetic_boundaries`
(переполнение сложения; usize::MAX+0; максимально представимое значение;
32-бит ветка try_from — платформозависимая часть).

### Дополнительные копии PCM (пик памяти на одну реплику)

Одновременно существуют: буфер реплики (≤ лимита 21,6 млн сэмплов ≈ 86,4 МБ
f32) + обрезанная копия `trim_edges` (ещё ≤86,4 МБ; третья копия устранена
`drop(pcm)`); выход SoundTouch ≤ входа (tempo > 1 — ускорение; tempo ≤ 1 —
обход без обработки, копия 1:1). Итого пик ≈ 2× лимита ≈ 173 МБ на самую
длинную реплику — задокументированное поведение. Расширения выхода SoundTouch
относительно входа нет (tempo ∈ (1, max] по контракту планера; замедление
запрещено) — отдельный предел результата не требуется. Окно пула
(queue_cap+workers чанков) и буфер воркера лимитом реплики не ограничены —
это чанковые (не репликовые) объёмы, ограничены сверху размером чанка
(max_tokens/max_chunk_chars). Полный трек в RAM не накапливается (потоковый
sink, backpressure пула не изменены).

### Диагностика

`SrtOutcome.max_cue_pcm_len` — пик длины буфера одной реплики: инструмент
проверки соблюдения лимита (тест `multichunk_cue_peak_buffer_tracked`:
15 чанков + 14 пауз = 528 000 = точный ожидаемый пик, ≤ лимита).

### Тесты SRT.9A (8 шт., без ONNX)

1. PCM ровно по лимиту — принимается (пик == лимиту).
2. +1 сэмпл — ошибка с требуемым/разрешённым.
3. Превышение одним большим чанком (24000 при лимите 1000) — ошибка до
   копирования, числа в сообщении арифметические.
4. Превышение накапливается чанками (паузы 0) — ошибка на переходе границы.
5. Внутренняя пауза превышает лимит — ошибка ДО resize (600+12000→12600).
6. Граничные u64/usize — без паник/переполнений.
7. Пустой PCM — реплика корректно завершается.
8. Пик буфера многочанковой реплики == сумма PCM+пауз, ≤ лимита.
   Плюс обновлён `memory_limit_cue_is_error` (новая инварианта).
Все зелёные; поведение обычных реплик не изменилось (13 прежних тестов
srt_pipeline без правок ожиданий, кроме сообщения лимита).

## B. Безопасный обход каталогов SRT (SRT.9B)

### Исходная проблема

`crates/gui/src/srt_job.rs`, `collect_srt_files()`:
`path.is_dir()` СЛЕДОВАЛ по directory symlink / junction / reparse point
(риски: циклы, повторная обработка, чтение вне выбранной папки, попадание в
выходной каталог, неконтролируемая глубина); ошибки `read_dir` молча
глотались (отказ в доступе к корню выглядел как «нет файлов .srt»);
вложенный выходной каталог не исключался (результаты прошлых запусков
попадали в новый пакет).

### Решение — переиспользование проверенной инфраструктуры TXT

Новый общий вход `batch::plan_dir_tree(source, out_root, ext_pred)`
(ветка каталога `plan_batch` TXT теперь вызывает его же — поведение TXT
не изменилось, 30 batch-тестов зелёные, порядок сортировки тот же):
относительный путь без учёта регистра, затем точный). Алгоритм — действующий
`collect_files` (G3.1):

- тип записи — `DirEntry::file_type` (метаданные перечисления, БЕЗ
  следования по ссылкам);
- ЛЮБАЯ reparse-точка (symlink/junction, каталог ИЛИ файл, включая
  file-symlink на .srt) пропускается с предупреждением в журнал GUI;
  циклы невозможны по построению (ни одна ссылка не раскрывается);
- источник сам не может быть reparse-точкой (symlink_metadata +
  FILE_ATTRIBUTE_REPARSE_POINT / is_symlink на не-Windows);
- выход не должен проходить через reparse-компоненты
  (`ensure_no_reparse_components`), не может физически совпадать с
  источником (`same_path` + `physically_same` — ловит другой регистр,
  `.`/`..`, альтернативные пути);
- вложенный выходной каталог исключается из обхода (`is_under` +
  `physically_under` — работает и когда выход ещё не существует);
  размещать output внутри источника НЕ запрещено — исключение решает;
- недоступный вложенный каталог — предупреждение (контракт TXT-пакета);
  недоступный/несуществующий КОРЕНЬ — явная ошибка: в `execute_srt_batch`
  зонд `read_dir` ДО планирования («каталог-источник не читается …»,
  не маскируется под «нет файлов .srt»); пустой результат — «нет файлов
  .srt» только при реально прочитанном корне.

Дорогая каноникализация каждого файла не добавлялась (физическое сравнение —
только для каталогов выхода/источника, как в TXT).

### Тесты SRT.9B (10 шт., Windows, все выполнены РЕАЛЬНО)

Рекурсия с .srt/.SRT и детерминизмом; выход-внутри-источника исключён
(старые результаты не озвучиваются); отсутствующий на старте выход исключён;
совпадение источник==выход — ошибка (точное, другой регистр, `.`/`..`);
junction на внешний каталог и на родителя (цикл) — пропущены с
предупреждениями; две junction на один каталог — обе пропущены, физические
файлы не задвоены; dir symlink (сосед/родитель-цикл) — пропущены;
file symlink на .srt — пропущен; ошибки корня (несуществующий, файл вместо
каталога) — явные. Symlink/junction создаются в уникальных песочниках
`%TEMP%\srt9b_*`; при отсутствии прав тест громко сообщает SKIP (на стенде
Developer Mode — все ссылки создались, пропусков нет); рекурсивных удалений
нет (артефакты остаются в %TEMP% по правилам проекта). Дорожащее замечание:
ACL-тест реального отказа доступа не выполнялся (риск оставить песочницу
неудаляемой) — ветка та же, что у несуществующего корня (ошибка `read_dir`).

### Регрессия TXT

`plan_batch` использует `plan_dir_tree` для ветки каталога: 30 тестов
`batch::tests` зелёные, включая symlink/junction-кейсы G3.1; поведение
обычного пакетного синтеза TXT не изменилось.

## C. SoundTouch FFI (SRT.9C)

### Источники истины

Комплектуемый `third_party/soundtouch/soundtouch-2.4.1.tar.gz`
(SHA256 `e07abf20…6733`) → `source/SoundTouchDLL/SoundTouchDLL.h` +
`SoundTouchDLL.cpp`; собранная `SoundTouchDLL.dll` (SHA256 `E8E56D3D…C3F6`;
оба хеша сверены с NOTICE.txt). Именно эта пара «заголовок ↔ DLL» — эталон.

### Таблица C ABI (все 14 загружаемых функций)

| Функция | Сигнатура C-заголовка 2.4.1 | Rust (`extern "system"`) | Совпадает |
|---|---|---|---|
| `soundtouch_createInstance` | `HANDLE __cdecl f()` | `fn() -> Handle` (`*mut c_void`) | ✓ |
| `soundtouch_destroyInstance` | `void __cdecl f(HANDLE)` | `fn(Handle)` | ✓ |
| `soundtouch_getVersionId` | `unsigned int __cdecl f()` | `fn() -> u32` | ✓ |
| `soundtouch_getVersionString` | `const char *__cdecl f()` | `fn() -> *const c_char` | ✓ |
| `soundtouch_setSampleRate` | `int __cdecl f(HANDLE, uint)` | `fn(Handle, u32) -> c_int` | ✓ |
| `soundtouch_setChannels` | `int __cdecl f(HANDLE, uint)` | `fn(Handle, u32) -> c_int` | ✓ |
| `soundtouch_setTempo` | `void __cdecl f(HANDLE, float)` | `fn(Handle, c_float)` | ✓ |
| `soundtouch_setSetting` | `int __cdecl f(HANDLE, int, int)` | `fn(Handle, c_int, c_int) -> c_int` | ✓ |
| `soundtouch_putSamples` | `int __cdecl f(HANDLE, const float*, uint)` | `fn(Handle, *const c_float, u32) -> c_int` | ✓ |
| `soundtouch_receiveSamples` | `uint __cdecl f(HANDLE, float*, uint)` | `fn(Handle, *mut c_float, u32) -> u32` | ✓ |
| `soundtouch_flush` | `int __cdecl f(HANDLE)` | `fn(Handle) -> c_int` | ✓ |
| `soundtouch_numSamples` | `uint __cdecl f(HANDLE)` | `fn(Handle) -> u32` | ✓ |
| `soundtouch_isEmpty` | `int __cdecl f(HANDLE)` | `fn(Handle) -> c_int` | ✓ |
| `soundtouch_clear` | `void __cdecl f(HANDLE)` | `fn(Handle)` | ✓ |

Calling convention: `__cdecl` на Windows x64 — единственная конвенция,
эквивалент `extern "system"`/`extern "C"` (проект целится только в x64).
Количество сэмплов: в `putSamples`/`receiveSamples` передаются КАДРЫ
(деление на channels; для моно кадр == сэмпл) — соответствует комментарию
заголовка. Mono/stereo согласованы (`channels=1` на всех вызовах SRT).

### Ключевой вывод по «void-гипотезе»

Подозреваемые `FnSetSampleRate`/`FnSetChannels`/`FnPutSamples`/`FnFlush`
в **2.4.1 объявлены `int`**, а не `void` (в старых версиях SoundTouch они
были void — источник гипотезы). Реализация: `return 1` — успех, `return 0` —
неверный обработчик (проверка `dwMagic != STMAGIC`) ИЛИ пойманное
`std::exception`. Следовательно:
- сигнатуры Rust **корректны**, менять не нужно;
- проверка `rc == 0` в `put_samples` **корректна** и не создаёт ложных
  ошибок (реальная DLL: блочная подача 7777-сэмпловыми блоками даёт выход
  побитово равный целой подаче — ложных отказов нет).

### Обнаруженные и исправленные дефекты контракта

1. **NULL после `createInstance` не проверялся**: C-обёртка может вернуть
   NULL (код обёртки предусматривает `tmp = nullptr`); прежний код тут же
   вызывал `setSampleRate(NULL, …)` → разыменование нулевого указателя
   ВНУТРИ DLL (`sth->dwMagic` по адресу 0) — нативный краш процесса.
   Теперь `create_speech_instance` возвращает `Result`, NULL — явная
   ошибка `SetupFailed`.
2. **Возвраты настройки игнорировались**: `setSampleRate`/`setChannels`/
   `setSetting` (речевой профиль 40/15/8, AA, QUICKSEEK) теперь
   проверяются (rc == 0 → `SetupFailed` с именем настройки, destroy
   обработчика) — «битая» DLL не может молча изменить речевой профиль.
3. **`rc` от `flush` игнорировался**: flush возвращает 0 при сбое —
   молчаливая потеря хвоста реплики. `finish()` теперь возвращает
   `Result`, ошибка прокидывается в `process_cue`.

Новый вариант ошибки `SoundTouchError::SetupFailed(String)`. Обёртка не
переписывалась — изменения точечные, по найденным несоответствиям.

### Residual-риски (задокументировано, не устранимо с нашей стороны)

- `soundtouch_createInstance` в C-обёртке НЕ обёрнут try/catch: бросающий
  `new` при нехватке памяти пробрасывает C++-исключение через FFI (все
  остальные функции ловят std::exception внутри себя). Практически
  недостижимо (OOM), но задокументировано.
- Ошибка «старой версии DLL» (UnsupportedVersion) покрыта кодом
  (version_id < 20_400), но fixture-теста нет —fabricate DLL старой версии
  без компилятора невозможно; путь идентичен протестированному MissingExport.

### Speech-профиль (без изменений)

SEQUENCE_MS=40, SEEKWINDOW_MS=15, OVERLAP_MS=8, AA вкл, QUICKSEEK выкл;
только `setTempo` (без setRate/setPitch); tempo=1.0 — обход обработки;
новый instance на реплику; NaN/Inf-защита входа/выхода. Эталон
soundstretch -speech совпадает по длительности (SRT.3).

### Тесты SRT.9C (13 шт. на реальной DLL, +2 новых)

Загрузка точной версии 20401 (`version_is_2_4_x` дополнен фиксацией
`SOUNDTOUCH_BUILT_VERSION_ID`); все экспорты (загрузка резолвит 14;
kernel32 → явная `MissingExport("soundtouch_createInstance")` — реальный
модуль без экспортов); создание/удаление; mono f32 24 кГц; tempo ×1.1/×1.5/
×2.0; короткая (<1 c) и НОВАЯ длинная (60 c ×1.5) реплики; изоляция реплик
(побитовая); flush-хвост + rc; NaN/Inf; отсутствие ложных ошибок putSamples
(блочная подача побитово = целой); фактические длительности (±допуск);
отсутствующая DLL — явная ошибка. Регрессия speech-профиля — константами и
фиксацией версии.

## D. Регрессия и реальная приёмка (SRT.9D)

Все прогоны повторены ПОЛНОСТЬЮ (прежние 412 не считались автоматом):
`cargo test --workspace --release` — **430 passed / 0 failed / 0 cargo-
errors** (412 базовых + 18 новых SRT.9: 8 pipeline + 8 job + 2 soundtouch);
gui в sw-конфигурации — **186 passed / 0 failed** (+2 sw-протокола);
`cargo fmt --all -- --check` — OK; `cargo clippy --workspace --all-targets
--release -- -D warnings` — 0 (glow и sw отдельно). Golden-файлы не менялись.

Real CPU (модели Slow FP32 локально, SRT_TEST_ONNX_BASE): WAV
(4 реплики, побитовая идентичность повтора seed 42) + MP3 + пакет 2 файла с
подкаталогом — 3/3 за 44 c. Real CUDA (RTX 3060): WAV + Opus + пакет — 3/3
за 15 c. Ускорение доказано реальными данными лога таймингов: реплика [3]
синтез 6255 мс → лимит 5900 мс → **tempo ×1.06 применён, финал 5900 мс по
фактическим сэмплам**, реплика [4] ×1.02; «Озвучено реплик: 3 из 4»
(пустая разметочная пропущена); промежуточных WAV нет (by construction);
pitch не меняется (только setTempo, тесты изоляции).

Portable-приёмка (out/srt8_portable_acceptance.ps1, hardlink-песочница
комплекта g7 + новые EXE): portable-check OK оба SRT EXE (читают только
PocketTTS-GUI-Rust-srt.json), GUI-смоук открытие/закрытие exit 0 оба,

srt.exe → OPENGL32, srt-cpu → без GL, как задумано).

Память: A — автоматические тесты превышения (см. §A) зелёные;

(out/srt9_memory_probe.ps1): пик private bytes тестового процесса
